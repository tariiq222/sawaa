# Sawa deployment policy

## Authorization and branch workflow

`main` is the sole permanent branch after the [single-main cutover](single-main-cutover.md). Task branches start at current `origin/main` and merge through a PR with a merge commit after the required checks. Enforce the PR and checks on GitHub. Local hooks block direct pushes to `main`. Keep task commits and unrelated local changes intact.

- **«انشر» / «انشر للاستيج» / «انشر على الاستيج» / «ننشر»** authorizes a scoped commit, task branch push, PR merge into `main` and automatic staging verification. Report the staging URL, exact running SHA, deployment ID and manual test steps. A push resulting from a merge cannot start the production deployment job.
- **«ادمج في الإنتاج» / «انشر في الإنتاج» / «انشر للإنتاج» / «انشر للبرودكشن»** authorizes a manual production dispatch for the exact current `main` SHA the owner accepted on the active, verified staging deployment. The wording «ادمج في الإنتاج» requests this manual deployment of the accepted SHA. A newer merge before the hook requires fresh staging verification and owner acceptance.
- Keep a local `main` tracking `origin/main`. The launchd agent `sa.sawaa.main-sync` runs `scripts/sync-main.sh` every five minutes after installation with `scripts/install-main-sync.sh`. After a merge, run the sync and report divergence. Fast-forward only. Preserve unpublished commits and uncommitted changes.
- Branch retirement is a separate scoped cleanup after the new staging path is verified and all unique work and PRs are accounted for.

## Fixed staging publication path — owner-approved 2026-10-11

The only staging publication path is `build-images.yml` → successful complete image build → `scripts/openship/staging-deploy.mjs` → the existing OpenShip incoming deploy hook → observed runtime verification. Do not add another trigger or fall back to host builds, the ordinary Redeploy button, mutable image tags, or ad-hoc SSH container replacement when this path fails. Diagnose and repair this path.

- OpenShip staging project `proj_7M0RNj59nQnafh1m` follows `main`, uses `docker/openship/compose.prebuilt.yml`, and keeps git `autoDeploy=false`.
- The build matrix emits SHA-bound digest artifacts. Only after all build jobs succeed does the deployment job update the three application image variables to `ghcr.io/tariiq222/sawaa-<service>@sha256:<digest>` and call the hook. Moving tags never select the runtime.
- Before changing image variables, the orchestrator selects the candidate full SHA as the staging project’s temporary Git ref. The hook freezes that immutable source/config snapshot before the ref returns to `main`; a concurrent push cannot mix source and image revisions. If a run stops before triggering, it restores previous image refs; a lost trigger response fails for investigation. An interrupted job that leaves a SHA selected blocks subsequent publication until this same staging configuration is repaired.
- The hook targets exactly backend, dashboard and website with strict service scope. PostgreSQL, Redis, MinIO, their image variables and persistent mounts are outside an application deployment. Their container identities must remain unchanged.
- The prebuilt backend starts with `node dist/src/main.js`, without a migration credential or migration command. The orchestrator reads `_prisma_migrations` in a `BEGIN READ ONLY` transaction before and after publication; missing/failed/modified/unknown migrations block publication. The three exact historical checksum pairs already documented on 3 October are preserved as provenance in the staging verifier; this is not a repair, and no new exception is inferred. Schema changes require separately authorized migration work; do not bypass this gate.
- A merge into `main` and manual `gh workflow run build-images.yml --ref main -f target=staging` use the same staging job. OpenShip application publication is serialized across both environments. An older run stops if superseded before its hook call. A push after that check may leave a verified frozen older candidate briefly active; its receipt marks `sourceSuperseded=true` and the queued newer workflow follows. Never label older images with a newer source SHA.
- Required repository variables are `STAGING_PREBUILT_DEPLOY=true` and `OPENSHIP_STAGING_HOOK_ID`; required secrets are `OPENSHIP_STAGING_DEPLOY_TOKEN` (a project-scoped staging read/write token), `OPENSHIP_STAGING_DEPLOY_HOOK_TOKEN`, and the existing staging read token for other read-only release checks. Missing activation or credentials fails visibly rather than skipping publication. Never widen the deployment token to production or shared-server access.
- Updating the incoming hook's `actionConfig` or execution authority can rotate its token. Configure the final staging-only service scope first, then privately transfer the current hook credential directly into `OPENSHIP_STAGING_DEPLOY_HOOK_TOKEN`; never print it or include it in logs, reports or artifacts. HTTP 404 can mask a credential or execution-authority mismatch: diagnose and correct this same path, then rerun its failed GitHub deployment job using the existing build artifacts. A full manual publication still uses `build-images.yml` on `main` with `target=staging`.
- A successful deployment requires the hook-returned deployment to be active and ready, the three running image references to match the exact digests, backend `gitSha` to match the source SHA, HTTP 200 checks for API/website and the internal dashboard, unchanged infrastructure containers and unchanged migration metadata. Evidence is saved as the workflow artifact `staging-deployment-<sha>`.
- OpenShip `ready` can precede Docker health readiness. The staging verifier polls application `starting` for at most 20 observations, 15 seconds apart; each observation rechecks the active deployment, exact image refs and unchanged infrastructure. Unhealthy services, invalid identities or digest drift fail immediately. Success requires all six services `running`; a startup timeout fails the workflow.
- OpenShip may leave `commitSha` empty for a fully image-backed deployment. Only this staging path accepts that case: the recorded branch must be the exact immutable candidate SHA, all application digests must match the build artifacts, and live backend health must independently report that SHA. A populated contradictory commit still fails. Production prebuilt source has its own explicit verification requirements below.
- Every merge to `main`, including documentation and mobile-only changes, queues staging so the candidate SHA can be observed directly. A superseded run reports the actual verified runtime SHA.
- The owner manually accepts the observed staging SHA before production promotion. Staging publication never authorizes production. The owner separately approved the production prebuilt path on 2026-10-11; its gates are defined below.

The operational procedure is [the sawaa-release skill](../../.claude/skills/sawaa-release/SKILL.md). Changes to this path require a scoped reviewed PR, regression checks and live staging evidence; new instructions cannot silently redefine the mechanism.

## Fixed production publication path — owner-approved 2026-10-11

The owner explicitly approved adopting the staging mechanism in production and promoting the accepted application content. Production uses a manual `build-images.yml` dispatch on `main` with `target=production` and `accepted_sha=<full SHA>` → all images built on GitHub → `scripts/openship/production-deploy.mjs` → a production-project-scoped incoming hook → observed digest/source/runtime verification. A failed gate stops publication; host builds, mutable tags and SSH container replacement are not fallback paths.

- Project is exactly `proj_tsxe0sAW3u2AMSGO`, with `docker/openship/compose.prebuilt.yml`, branch `main` and `autoDeploy=false`. Preserve production database/provider settings and data mounts. The hook targets exactly backend/dashboard/website with strict scope; PostgreSQL/Redis/MinIO retain their identities and images.
- In the GitHub `production` environment, `SAWAA_PRODUCTION_ACTOR` identifies the owner-approved GitHub login for both the original dispatcher and any rerun. Administrators record `SAWAA_PRODUCTION_ACCEPTANCE` with `owner`, `acceptedSha`, `stagingDeploymentId`, `stagingRunId` (the successful GitHub staging run ID as a number), `stagingVerifiedAt` (the staging artifact's `observedAt`) and the later `ownerAcceptedAt`. The workflow reads the immutable evidence artifact from that same successful main run and checks its deployment ID, timestamp and SHA against the acceptance. The requested, accepted, built and live staging SHAs must match. Staging must still be ready with its accepted deployment ID and independent backend health proof when the hook is about to run.
- `PRODUCTION_BACKUP_EVIDENCE` records the production project, previous deployment/source SHA, protected backup path, creation time, checksum verification, isolated successful database restore, identical source/restored migration/Client/Booking/Payment counts, readable MinIO archive and valid Redis RDB. The receipt must be under 24 hours old and match the still-active rollback deployment.
- Required variables: `PRODUCTION_PREBUILT_DEPLOY=true`, `OPENSHIP_PRODUCTION_HOOK_ID`, `SAWAA_PRODUCTION_ACTOR`, the environment-scoped `SAWAA_PRODUCTION_ACCEPTANCE`, and the backup JSON above. Required secrets: `OPENSHIP_PRODUCTION_DEPLOY_TOKEN` (Deploy & manage limited to this project, plus View of the public `tariiq222/sawaa` repository metadata with source-file access disabled), `OPENSHIP_PRODUCTION_DEPLOY_HOOK_TOKEN`, and the existing staging read-only token for the acceptance gate. The hook captures this scoped token's execution authority: a project grant alone fails the repository-access gate before creating a deployment. When correcting that binding, rearm the same three-application hook with the corrected limited token, privately save its rotated credential, and rerun the failed deployment job using the existing successful image artifacts. Never reuse the staging write credential for production or widen authority to repository writes, other projects or the server.
- Separately authorized additive migrations run before application publication through `prisma migrate deploy`, after backup and isolated restore/migration validation. The application orchestrator reads migration metadata in SELECT-only read-only transactions and requires all expected migrations already complete, their checksums valid under the established exact provenance, and unchanged metadata after publication. The runtime backend starts directly without a migration command; remove the migration owner credential from its runtime scope during setup.
- The hook snapshots a temporarily selected immutable main SHA and only the three digest-pinned application image variables. Restore `main` after snapshot capture. Source changes before the hook stop publication and compensate refs; a lost hook response fails for investigation without retrying or racing the submitted images.
- Image-backed production may omit OpenShip `commitSha` only when its recorded branch is the exact frozen main SHA, all three canonical digest references match the successful build manifests, independent backend health reports that SHA, and production remains explicitly configured for prebuilt mode with auto-deploy disabled. Contradictory commit metadata fails. This is independent production authorization, not an inferred extension of the staging exception.
- Success requires active ready deployment, all six services running, exact application digests, backend SHA, public API/site/dashboard/files HTTP 200, unchanged infrastructure and unchanged migrations. Save `production-deployment-<sha>` as a GitHub artifact and record the observed release receipt. A main advance before the hook rejects the candidate. If it advances after the hook, record `sourceSuperseded=true` alongside the independently verified deployment and its exact SHA.
- Dispatch `gh workflow run build-images.yml --ref main -f target=production -f accepted_sha=<full SHA>` using the approved login. Rerun only the failed deployment job when its image artifacts are available and the active accepted staging SHA and backup still match. Use a fresh dispatch to rebuild the images. Rerun only release metadata if publication was verified and tagging failed. The release metadata job runs only after production verification succeeds and tags the verified SHA.

### Staging provider configuration

- FCM backend credentials use `FCM_PROJECT_ID`, `FCM_CLIENT_EMAIL` and `FCM_PRIVATE_KEY` in the staging project's secret environment. The mobile Firebase client configuration is not a server credential. Provisioning a new Google service account, access grant or private key requires the applicable security confirmation; keep keys outside Git, logs and evidence artifacts.
- For a provider-only configuration change, update only the staging project's environment, then publish through the same `build-images.yml` path. OpenShip names this project's runtime environment `production`; the project ID must still be `proj_7M0RNj59nQnafh1m`. Never use the production project's environment or change application database settings to enable staging FCM.
- Verify Firebase Admin initialization and a provider validation-only request separately from actual device delivery. Initialization alone does not prove delivery. Without an FCM provider, new resilient push dispatches are recorded as skipped, not sent; never rewrite historical notification rows or replay messages as part of configuration.
- Moyasar verification uses test-mode credentials and read-only provider lookups when database writes are prohibited. A native SDK UUID reservation can legitimately return 404 before a payment exists; only validated reservation provenance permits suppressing its missing-reference warning. A successful lookup or local regression test does not establish a completed payment flow.

## Data and failure boundaries

- Staging and production have separate databases and credentials. Promote code and compatible additive migrations, never staging data into production.
- If a gate fails, stop at that gate and report the evidence. Do not promote automatically just because CI passed.
- A code rollback does not authorize restoring an old production database or losing newer customer data. Assess compatibility and obtain explicit authorization for destructive recovery.
- Keep credentials out of Git, logs and reports.

## Merge checks for `main`

Local Woodpecker CI was removed on 2026-10-01 by owner decision. Do not run, reintroduce or require it. GitHub Actions was re-enabled for the repository on 2026-10-01 by the owner. The `merge-gate` workflow runs on pull requests into `main` and on pushes to `main`, with two jobs: `gate` and `critical-real-e2e` (the `test:e2e:critical` real-database suite on a disposable Postgres service). CI supplements the local checks below; it does not replace them.

Before a PR merges into `main`, run the local checks that match the changed surface, using the test matrix in the root `CLAUDE.md` (for example backend Jest specs and `pnpm openapi:sync` for endpoint changes, dashboard Vitest and smoke for dashboard flows, `pnpm --dir apps/mobile test`/`typecheck`/`lint` for mobile). Documentation-only changes need only `git diff --check`. Record the commands, the candidate SHA and the results in the PR. A failed or skipped required check blocks the merge; if the candidate changes after verification, verify the new content before merging.

Checks use local disposable test infrastructure. Never use development, staging or production credentials or databases. Passing checks do not replace live verification of the changed flow or the owner's manual staging test.

The production promotion rules above remain in force.
