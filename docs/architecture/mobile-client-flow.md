# Sawaa mobile client flow

This document explains the implemented mobile route and data contracts. Keep it in sync when changing client discovery, booking, authentication handoff, or appointment follow-up. The clinic/service data model is defined in [clinic-service-booking-contract.md](clinic-service-booking-contract.md).

## Navigation

- Client tabs follow Home (`/(client)/(tabs)/home`), Appointments (`/(client)/(tabs)/appointments`), Explore (`/(client)/(tabs)/explore`), Account (`/(client)/(tabs)/account`). The guest dock keeps the same four destinations through `/home`, `/appointments`, `/explore`, and `/guest-account`. The guest appointments page explains why sign-in is needed and keeps the public dock visible. Staff routes live under `/(employee)` and must not reuse client guards or booking actions.
- Home presents search, the signed-in next appointment, four image shortcuts for clinics, specialists, packages, and programs. Below these cards, assessment services are selected from the real assessment category/department using `lib/assessment-services.ts` and open public service detail with the actual service ID. The same detail screen continues into the signed-in or guest booking route. Legacy catalogs without a semantic category key use explicit group-name aliases in that helper; never create rows from screenshot labels. These shortcuts open the existing catalog destinations; do not duplicate data fetching or booking logic in the cards. Tapping a clinic opens its scoped detail. Guests can browse it through public navigation, but authentication is required at booking confirmation.
- Explore starts with five categories and searches clinics, visible bookable services, public bookable specialists, packages, and programs. Clinic results open clinic detail; guest service results open public service detail with `serviceId` and, when applicable, `clinicId`, then practitioner selection. Signed-in service results can open the scoped practitioner list. Package and program results keep their distinct detail and purchase/enrollment paths. Never display a service base price as the appointment price: the practitioner's duration and delivery option owns the charged amount.
- Clinic detail currently has no authored clinic explanation because the public clinic/catalog contract has no description field. Do not invent marketing copy from counts or service names; adding explanations requires a separately reviewed catalog field, editor, API, and content entry.
- A DIRECT clinic has one hidden internal service for backend booking. Never show its internal label or its default price in discovery or confirmation. The user's confirmation displays the clinic name and the practitioner's carried price. A SERVICES clinic presents its visible services. Supporting services without a category remain discoverable, but an unknown non-null category reference does not qualify as a valid service grouping.
- The practitioner list defaults to all relevant bookable specialists. `available today` is an opt-in filter because future appointments may still be possible. Keep request failures distinct from an empty result and provide retry.

## Booking context and authentication

- Preserve `clinicId` (optional for supporting services), `serviceId`, and `employeeId` from discovery through `booking/[serviceId]`, schedule, confirm, and payment. The selected delivery type, branch, time, duration option, currency, and charged price also travel with the booking draft. Do not infer a clinic from an employee name or department.
- `features/booking/guest-booking-flow.ts` owns the serialized guest draft and auth continuation helpers. A draft is validated before resumption. Legacy drafts without `clinicId` remain valid. Do not send a malformed draft into payment.
- Login, registration, OTP, review login, and password recovery preserve both the booking draft and an optional guarded-route redirect. After authentication, a valid client booking draft takes priority. Otherwise, resume only a role-compatible in-app redirect; fall back to the role's home. Never follow external or auth-loop redirects.
- `features/booking/confirm-catalog.ts` resolves only the requested service and clinic context. DIRECT resolution may read the raw public catalog to find the hidden service, but only for its selected clinic. Category-less supporting services may use a visible, active raw-catalog fallback. Never substitute a service from a different clinic or expose hidden services as standalone entries.
- The payment screen stores a created booking and nullable invoice ID per client and exact immutable draft before payment initialization. On re-entry it reads the booking from the server and resumes only a matching pending invoice; an authenticated retry link with a known booking and invoice can recover even without local storage. An invoice-less confirmed booking goes to success. Invalid or uncertain stored state fails closed instead of issuing a second create request. A lost response from the initial booking-create POST remains ambiguous because the mobile API exposes no idempotency key. Browser return is not payment confirmation; server status determines the screen. Moyasar callback, refund, and invoice internals are outside this UI contract.

## Appointments, packages, and staff

- `Appointments` separates upcoming, past, and cancellations. The cancellations tab includes pending cancellation requests because the current list API returns them there; each request must visibly say it is pending approval. A request is not a cancelled appointment. Client cancellation is unavailable for group enrollments and completed/terminal states.
- A completed appointment can offer rating only when the mobile booking detail indicates no stored rating. The mobile `GET /mobile/client/bookings/:id` read path adds `hasRated` from the stored rating for a client-scoped request; the session-local fallback suppresses the action immediately after a successful submission. The existing `type` field identifies group appointments so they cannot show individual cancellation actions.
- Package purchase/credit booking and group enrollment use their own existing screens and existing booking/payment status. Do not route them through the individual service/practitioner sequence.
- Staff calendar bookings open their staff appointment detail. Staff role redirects after OTP stay under `/(employee)`; client redirects stay within the client/public area. Staff can only perform actions already authorized by existing guards and backend state rules.

## Glass surfaces

Use `theme/components/Glass` for cards, search containers, and navigation surfaces. The approved reference is the translucent aqua clinic row with a thin luminous rim and dark text. All legacy variants share the same optical treatment; never simulate it with `glass.opaqueBg` or add an opaque background to a Glass wrapper. Keep opaque fallbacks for reduced-transparency accessibility and semantic colors for actions/status. Home image shortcuts use the same glass caption and the existing discovery assets.

## Change and verification rules

1. Read `apps/mobile/CLAUDE.md` and [the clinic catalog contract](clinic-service-booking-contract.md) before editing. Use query hooks for server reads, theme tokens for colors, i18n keys for new copy, and keep route files under 350 lines.
2. Add a focused test for a behavior change, including failure, empty, deep-link, or stale-data states when relevant. Verify the chosen route target actually exists and carries required IDs.
3. Run `pnpm --dir apps/mobile typecheck`, `pnpm --dir apps/mobile exec jest --runInBand --coverage=false`, and `pnpm --dir apps/mobile lint` after integrating mobile changes. Root workspace commands do not cover mobile.
4. Keep backend contract changes separate: endpoint/DTO changes require backend tests and an OpenAPI snapshot generated from this checkout (`pnpm --filter=backend run openapi:build-and-snapshot`), followed by `pnpm --filter=dashboard run openapi:generate`; package API client edits are manual. `pnpm openapi:sync` fetches a running server, so use it only when that server is proven to be this checkout. Do not alter auth guards, provider flows, encryption constants, or migrations as part of a screen change.
5. Device acceptance requires an isolated build/runtime and an actual walkthrough of guest discovery, DIRECT and SERVICES booking, auth recovery, payment pending/confirmed, cancellation request, package/group, and staff routes. Passing Jest or TypeScript does not establish device or provider behavior.
