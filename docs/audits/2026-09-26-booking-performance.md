# تدقيق أولي لأداء الحجز في sawaa.sa

> هذا تدقيق للكود مع عينتين من طلبات HTTP عامة، وليس قياس Lighthouse أو تسجيل شبكة لمتصفح يكمل رحلة حجز. لا يثبت سبب البطء الذي حدث أمس أو زمنه الفعلي. تاريخ اسم الملف من الجلسة السابقة وليس تاريخ قياس مؤكد.

## الخلاصة المرتبطة بشكوى المستخدم

خطوة «بياناتك» وتسجيل الدخول تظهر **داخل معالج `/booking` نفسه**؛ لا ينتقل المستخدم في هذه اللحظة إلى `/login`. أقوى تفسير قابل للتحقق من الكود لتأخر *ظهور* تلك الخطوة هو أن `ClientInfoStep` ينتظر فحص الجلسة عبر `GET /public/me`، ويستبدل نموذج الدخول بمؤشر تحميل حتى ينتهي الطلب (`apps/website/features/booking/client-info-step.tsx:73,178-195`). يحتاج إثباته في الإنتاج إلى سجل Network لهذه الخطوة.

إذا كان التأخير **بعد الضغط على زر تسجيل الدخول**، فهذا مسار مختلف: ثلاث عمليات تُنتظر بالتتابع: `clientLoginApi` ثم `getMeApi` ثم `refetch` (`client-info-step.tsx:89-120`). رد تسجيل الدخول لا يحمل ملف العميل، بل `clientId` فقط (`apps/backend/src/api/public/public-auth.controller.ts:78-88` و`packages/shared/types/client-auth.ts:93-95`)، ولذلك `/public/me` ضروري في العقد الحالي، لكن إعادة `refetch` عقب `getMeApi` تبدو مرشحة للإزالة بعد التحقق من تحديث كاش TanStack Query والمحافظة على قواعد انتهاء الجلسة.

## قياسات محدودة أُخذت في الجلسة السابقة

من جهاز الفحص، طلب واحد لـ`https://sawaa.sa/booking` أعاد 200 وTTFB قرابة 0.488 ثانية وحجم HTML 37,841 بايت؛ طلب واحد لـ`https://sawaa.sa/login` أعاد 200 وTTFB قرابة 0.469 ثانية وحجم HTML 53,079 بايت. `curl` قاس HTML فقط ولم يقس تنزيل JS أو تنفيذ React أو API أو اتصال المستخدم أمس. صفحة `/login` ليست الخطوة النهائية في المعالج، لذلك لا يجوز اعتبار رقمها زمناً لتلك الخطوة أو استنتاج تحسن مضمون منها. لا توجد نتائج Lighthouse أو Web Vitals موثقة هنا.

## ما يثبته الكود — حسب الصلة والأولوية

1. **بوابة تحقق الجلسة عند عرض نموذج الدخول — أولوية عالية للتحقق.** `useCurrentClient` يستدعي `/public/me` عندما تكون قراءات الجلسة مفعّلة؛ لديه `staleTime` قدره 15 ثانية وإعادتان للمحاولة في أخطاء الشبكة غير النهائية (`apps/website/features/auth/use-current-client.ts:78-101`). `getMeApi` يفرض مهلة 10 ثوانٍ **لكل محاولة** (`apps/website/features/auth/auth.api.ts:32,61-70,119-150`). بالنسبة للمستخدم غير المسجل، المتوقع رد 401 بلا retries من طبقة Query، لكن قد يوجد مسار تجديد جلسة في عميل API يحتاج قياساً. عند انتهاء الطلب أو الخطأ يظهر النموذج؛ لا نستطيع الجزم بزمن الانتظار الإنتاجي من الكود وحده. افحص زمن `/public/me` وحالة HTTP وسبب أي refresh أو retry في Network وسجل الخادم. من خيارات الإصلاح بعد القياس: بدء فحص الجلسة قبل الوصول للخطوة، أو تقديم واجهة غير حاجبة **مع منع السماح بتأكيد الموعد قبل حسم حالة المصادقة**.

2. **طلبات إضافية بعد إدخال بيانات الدخول — أولوية عالية إذا كان البطء بعد الإرسال.** `POST /public/auth/login` ثم `/public/me` ثم إعادة جلب `/public/me` بشكل متتابع؛ راجع أولاً جدوى `refetch` الثالث مع اختبارات للحالات: دخول ناجح، جلسة منتهية، خروج متزامن، فشل شبكة. تغيير استجابة API لتتضمن profile سيطال backend والعقد المشترك والعميل ويحتاج موافقة المالك على تغيير auth؛ ليس إصلاحاً أحادي الملف. مهلة 10 ثوانٍ الظاهرة في `auth.api.ts` تخص `/public/me`، **وليست دليلاً على أن كل طلبات السلسلة لها المهلة نفسها**.

3. **تحقق الخادم لطلبات الجلسة — مساهم محتمل، غير مقاس.** `ClientJwtStrategy.validate` يجلب سجل Client من قاعدة البيانات ليتحقق من التفعيل والحذف و`tokenVersion` (`apps/backend/src/modules/identity/client-jwt.strategy.ts:43-73`)، ثم `GetMeHandler` ينفذ قراءة أخرى (`apps/backend/src/modules/identity/client-auth/get-me.handler.ts:21-42`). اقرأ timing للطلب واستعلامات Prisma قبل اقتراح cache؛ تخزين نتيجة التحقق دون invalidation صحيح قد يؤخر إبطال الجلسة، وهو تغيير مصادقة حساس يحتاج موافقة مالك النظام.

4. **تكلفة الدخول نفسه — مساهم محتمل بعد الإرسال.** `ClientLoginHandler` ينفذ فحص قاعدة بيانات ثم Redis ومقارنة كلمة المرور ويحدث `lastLoginAt`؛ في حالة المحاولات السابقة يحدث صف العميل مرتين بالتسلسل (`apps/backend/src/modules/identity/client-auth/client-login.handler.ts:34-112`). قياس زمن كل مرحلة سيحدد إن كانت مؤثرة، ولا يُنصح بتغيير كلفة hashing أو حدود الحماية لمجرد تحسين السرعة.

5. **تحميل صفحة الحجز الأولية، لا الانتقال الداخلي للخطوة — منفصل.** `RootLayout` ينتظر branding (`apps/website/app/layout.tsx:58-65`)؛ fetch له cache إعادة تحقق 60 ثانية ومهلة 1500ms مع fallback (`apps/website/features/branding/branding.api.ts:27-53`). يمكن أن يؤثر على تحميل الصفحة أول مرة أو التنقل الكامل، لكن خطوات المعالج client-side، فلا يصح جمع 1.5 ثانية تلقائياً مع زمن ظهور النموذج في الخطوة النهائية. راجع cache headers وبيئة الاتصال الداخلية قبل تعديل TTL، لأن رفع TTL يؤخر تغييرات الهوية البصرية. الـ middleware يفحص cookies ويبني CSP (`apps/website/middleware.ts:95-141`) لكن ليس لدينا قياس يثبت كلفة 20–50ms أو أنه السبب.

6. **بيانات المواعيد/الاختيار — مشكلة مجاورة.** ثلاثة استعلامات عامة تبدأ عند فتح المعالج (`apps/website/features/booking/use-booking-wizard.ts:85-120`) وهناك حسابات إتاحة في backend؛ قد تؤثر على مرحلة اختيار الموعد، لا تثبت أنها سبب انتظار نموذج الدخول بعد اختيار الساعة. لا تغيّر `create-booking` أو عزل المعاملات من أجل الأداء بلا موافقة واختبارات وسيناريو دفع تجريبي؛ هذه منطقة حساسة.

## تصحيحات مقارنة بالمسودة السابقة

- لا يوجد انتقال تلقائي من آخر خطوة إلى `/login`؛ النموذج داخل `/booking`.
- `cache()` مع `next: { revalidate: 60 }` لا يعني طلب branding جديداً في كل تنقل؛ لا نملك سجل hit/miss للإنتاج.
- عدد ملفات JS وحده لا يثبت مشكلة حجم؛ وnamed imports من `lucide-react` لا تعني تحميل المكتبة كاملة. أي ادعاء عن حجم الباندل أو نسبة تخفيض يحتاج قياساً.
- تقرير الوكيل السابق قال إن إنشاء رقم الموعد يفتقد الفهرس: هذا غير صحيح؛ migration `apps/backend/prisma/migrations/20260605120000_enforce_unique_indexes_hard/migration.sql:57-67` ينشئ فهرساً فريداً على `bookingNumber`.
- `findFirst` بشرط المفتاح الأساسي لا يعني بالضرورة sequential scan؛ يلزم `EXPLAIN ANALYZE` لإثبات خطة الاستعلام.
- `bcryptjs` قد يستهلك CPU لكنه لا يثبت حجب event loop طيلة عملية async أو زمن 250ms في هذا الخادم دون profiling.
- لا توجد قياسات تبرر تقديرات «30–41.5 ثانية»، «تحسين 30%»، أو وصف Sentry بأنه سبب TTFB.

## طريقة إثبات السبب في الإنتاج من دون إنشاء موعد أو إرسال بيانات حساسة

1. افتح DevTools → Network مع Preserve log وDisable cache (على جهاز اختبار/جلسة منفصلة)، واذهب في معالج الحجز حتى **قبل** خطوة «بياناتك». لا تضغط تأكيد الموعد أو الدفع.
2. سجّل وقت النقر على «التالي» ووقت ظهور النموذج/انتهاء «جارٍ التحقق من حسابك»، وراقب طلبات `GET /api/v1/public/me` وطلبات refresh إن وجدت: status، Waiting/TTFB، عدد المحاولات، وأي 401/403/429. لا تشارك قيم cookies أو كلمة المرور أو معلومات المرضى.
3. قارن جلسة خاصة بلا تسجيل دخول مع جلسة اختبار مسجلة، ثم إن كان التأخير **بعد إرسال بيانات الدخول** قِس زمن `POST /public/auth/login` وطلبَي `/public/me` باستخدام حساب اختبار فقط. لا نحتاج بيانات دخول المستخدم هنا.
4. اربط timestamps بسجلات backend/Prisma وCPU/Redis/DB pool. اعتمد p50/p95/p99 من عدة محاولات ومن اتصال سعودي/جوال بدل عينة `curl` مفردة.

**أول إصلاح مرشح بعد القياس:** في `client-info-step.tsx` إزالة إعادة fetch المتكررة بعد نجاح `/public/me` مع تحديث كاش الجلسة بشكل سليم، أو نقل فحص حالة الدخول إلى مرحلة مبكرة حتى يظهر النموذج فور وصول المستخدم. لم تُطبّق تغييرات برمجية على الموقع أو الإنتاج في هذا التدقيق.
