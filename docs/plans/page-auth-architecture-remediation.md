# خطة إصلاح بنية الصفحات وحالات الضيف/المسجّل — سواء

**نوع المستند:** خطة تنفيذ ومراجعة، لا تفويض بتنفيذ التغييرات أو نشرها. **الأولوية:** P0 إصلاح تأكيد الدفع C (بعد قرار المالك) وتنقل الرئيسية B؛ P1 رجوع الإشعارات H وإزالة الطلب المهدور F؛ P2 توثيق/تنظيف مشروط G. **خط الأساس:** `develop` عند `1a1838583`؛ تعاد معاينة الحالة قبل كل خطوة. **النطاق:** `apps/mobile` و`apps/website`، مع تحقق تكاملي للدخول والحجز؛ لوحة الإدارة فحص/قرار منفصل لا تغيير تلقائي. **مبدأ التنفيذ:** إصلاح سلوك مثبت أولًا، ثم إزالة الازدواجية الحقيقية، ثم تحسينات اختيارية بعد قياس. لا مساواة بين اسمَي مسار متشابهين وبين نسخ UI متطابقة.

## 2) خريطة الاعتماد والتنفيذ

```text
A  خط أساس ومصفوفة مسارات/اختبارات إعادة إنتاج
├─ B  إصلاح تنقل الجوال ودور المستخدم ── H  رجوع الفتح البارد لشاشات مهمة ── D  تحقق جوال وتوثيق الإصدار

```

بعد A، يمكن تنفيذ B ومسار الموقع بالتوازي في worktrees منفصلة؛ H يتبع B، وC ينتظر اختيار المالك لسياسة تأكيد الدفع، وF يتبع دمج C أو قرار تأجيله حتى تُراجع جلسات الموقع في سياق واحد. إن تعطل قرار C يمكن تنفيذ F مع اختبارات دخول الحساب كاملة ثم إعادة فحصها بعد C؛ التوازي التقني للملفات لا يغني عن بوابة التكامل. كل خطوة تغيير في PR صغير مستقل، ولا merge أو deploy بموجب هذه الخطة. اقرأ `apps/mobile/CLAUDE.md` أو `apps/website/CLAUDE.md` قبل تعديل التطبيق المعني. إن لم توجد بيئة اختبار بدفع تجريبي/جلسة منتهية، سجّل التحقق الحي «غير منفذ» ولا تستبدله بتأكيد نجاح الاختبارات.

### B — أصلح الرئيسية والرجوع في تطبيق الجوال فقط

**المالك/الملفات المرشحة:** `apps/mobile/app/home.tsx`، `apps/mobile/app/(client)/(tabs)/home.tsx` (فحص role في الصفحة المشتركة)، `apps/mobile/lib/navigation.ts`، مواضع استخدام `goBackOrHome`، واختباراتها تحت `apps/mobile/app/__tests__/` و`apps/mobile/lib/__tests__/`. لا تغير حارسي الدور أو تخزين الرموز أو API. الأسماء هنا ترشد للفحص وليست إذنًا لتعديل كل المواضع.

**القرار الهندسي المفضّل:** اجعل مسار `/home` العام يعمل للضيف وحده، وتحوّله للعميل ذي الجلسة المكتملة إلى `/(client)/(tabs)/home` (والـ staff إلى `/(employee)/(tabs)/today` إن وصل إلى المسار العام). اختيار تحويل صريح داخل alias العام يحمي كل المداخل الحالية بما فيها `goBackOrHome` وروابط عميقة قديمة؛ يمكن جعل الرجوع role-aware أيضًا إذا أثبتت تجربة التنقل الحاجة، لكن لا تكرر المنطق في كل زر. تحقق من أثر `PersistGate` في `app/_layout.tsx:79-81` و`stores/store.ts:16-20`: ينتظر إحياء auth (token وuser معًا)، لكنه لا يثبت اكتمال تحقق profile الذي ينفذه `app/index.tsx:24-89` عند المرور عبر index. عند فتح `/home` مباشرةً لا تفترض حصول هذا التحقق؛ لا تضف بوابة عالمية جديدة تلقائيًا، بل اختبر ضيفًا، عميلًا بحالة محفوظة سليمة، جلسة منتهية، وtoken بلا user. إن رُصدت فجوة، استخدم انتظارًا أو تحققًا محليًا محدودًا لا يكسر العرض العام؛ لا تجعل alias يعتمد على `index.tsx` الذي لم يُعرض. راجع `getPrimaryRole(user)` في `types/auth.ts:70-80`؛ غياب الدور يعود إلى client للتوافق، لكن وجود token/user وحده لا يعني أنه عميل. يجب ألا ينفّذ الموظف `useHome(true)` عند عرض الشاشة المشتركة. في `services/native-session-state.ts:35-49,74-86` تكتمل عملية مسح Redux قبل تنفيذ `.then(() => router.replace('/home'))` في logout العادي؛ اختبر هذا الترتيب والتزامن مع جلسة جديدة، ولا تغيّر السياج `isLogoutFenceActive()` بلا فشل مُعاد إنتاجه وموافقة auth. طبّق إعادة توجيه منفصلة ومؤهلة للدور بعد اكتمال حالة الجلسة، وتجنّب `router.replace` أثناء render؛ استخدم النمط المشروع المعتمد للموجّه. احتفظ بإمكانية الرجوع إلى الضيف بعد `authService.logout()`؛ تأكد أنه يمحو الحالة قبل `/home`، ولا توجه حالة معلّقة صالحة ظاهريًا إلى تبويبات العميل.

**معايير القبول:**
- B1: فتح `/home` بلا جلسة يعرض `GuestDock` ولا يطلب بيانات `useHome` الخاصة.
- B2: وصول `CLIENT` مسجّل إلى `/home` صراحةً أو عبر `goBackOrHome` بلا history ينتهي في shell العميل مع تبويباته المعرفة في `_layout.tsx`، لا الشاشة الجذرية بلا dock.
- B3: وصول `STAFF` إلى `/home` لا يعرض بيانات عميل أو يحوله خطأً إلى حارس العميل؛ يعود إلى مساره أو إلى حالة ضيف بعد logout حقيقي حسب الجلسة.
- B4: فتح `/(client)/booking/[serviceId]` أو `schedule/confirm` من رابط بارد، ثم الرجوع: no history وhistory طبيعي يحققان السلوك المتوقع؛ يتم حفظ معامل العيادة/الخدمة والتكملة بعد OTP، ولا تتغير صلاحيات المجموعة.
- B5: لا loop بين `/home` و`/(client)` أو `(employee)`؛ التعليق القديم في `lib/navigation.ts:5-10` يحدّث إلى الحقيقة الجديدة.
- B6: فتح `/home` مباشرة أثناء استعادة SecureStore لا يظهر واجهة ضيف خاطئة بشكل مستقر ولا يستدعي بيانات عميل قبل تحقق الدور؛ يتم إظهار حالة انتظار محدودة أو الانتقال إلى shell الصحيح بعد اكتمال الجلسة.

**اختبارات تُكتب قبل التعديل:** حالات root `/home` لثلاث حالات auth ومرحلة hydration، اختبار الرجوع بلا history من شاشة العميل، اختبار العودة الطبيعية مع history، سيناريو logout، وحالة staff؛ اختبارات `app/__tests__/index.test.tsx` والحراس الحالية وتكملة OTP تبقى خضراء. لا تعتمد على اختبار HomeScreen وحده؛ اختبر *ملف alias* والوجهة؛ `shared-home.test.tsx` القديم يختبر المكوّن فقط.

### H — عالج الرجوع من الشاشات العميقة المفتوحة بلا سجل، بعد B

**الملفات المرشحة:** في PR الإلزامي `apps/mobile/app/(client)/appointment/[id].tsx`، `apps/mobile/app/(employee)/appointment/[id].tsx`، مع اختبارات تفاصيل الشاشات و`lib/__tests__/navigation.test.ts`. إن ثبُت وصول بارد من رابط عميق إلى العيادة/الممارس فليكن PR ثانٍ لـ `apps/mobile/app/(client)/clinic/[id].tsx` و`apps/mobile/app/(client)/employee/[id].tsx` فقط. أظهرت مراجعة المسارات وجود `router.back()` مباشر في نحو 37 موضعًا؛ **لا** تستبدلها جميعًا. افحص فقط زر الرجوع في التفاصيل التي يمكن فتحها عبر إشعار/رابط عميق ومن دون history. لا تبدّل أزرار رجوع نموذج تعديل أو wizard أو زر يعود إلى حالة دفع معلقة.

**خطة عمل صغيرة:** اكتب اختبارات للضغط على زر الرجوع حين `canGoBack()=false` ثم حين `true` في شاشة موعد العميل والموظف؛ مع الحفاظ على الوجهة المؤهلة بالدور. استخدم بوابة B الجديدة حين ينتهي الأمر إلى `/home`، أو وجهة دور محددة إن كانت أنسب لعقد الشاشة. لا تغير إجراءات الرجوع بعد mutate/cancel/reschedule دون تتبعها. ابدأ بالموعد الذي تفتحه `utils/notification-deeplink.ts:34-38`؛ ضم العيادة/الممارس فقط إذا ثبت مدخل deep link بلا history. على Android وiOS اختبر ضغطة رجوع داخل التطبيق وزر النظام، ثم العودة الطبيعية حين يوجد سجل.

**قبول H:** H1 فتح تفاصيل موعد عميل من إشعار بارد ثم رجوع لا يعلق ولا يفقد tab shell؛ H2 موظف من رابط تفاصيل موعد يعود إلى shell الموظف لا واجهة عميل؛ H3 إذا يوجد سجل فيرجع إلى الشاشة السابقة، مع حفظ سياق الموعد؛ H4 لا تتأثر تدفقات تعديل الحجز أو دفع الفاتورة. اختبارات `pnpm --dir apps/mobile exec jest --runInBand --coverage=false ...` لملفات الشاشات ذات العلاقة، ثم typecheck/lint/full test كما في B. تحديث سجل إصدار الجوال لكل PR. **التراجع:** استرجاع تعديلات أزرار التفاصيل فقط؛ احتفظ بإصلاح B المستقل.

**تحسين لاحق مشروط وليس جزءًا إلزاميًا من B/H:** في خطوة منفصلة بعد اختبار bare deep links، يمكن حراسة `app/explore.tsx` و`app/appointments.tsx` و`app/guest-account.tsx` للمسجّل حتى لا تعرض واجهة ضيف. هذا ليس مبررًا لحذفها؛ PR صغير مع اختبار guest/client/staff لكل شاشة، وفحص عدم حصول redirect loop. لا تبدأ قبل قياس سلوك تلك الروابط على جهاز.

### C — قرار سياسة الصفحة ثم إصلاح تأكيد الدفع عند غياب جلسة الموقع

**ملفات مرشحة:** `apps/website/middleware.ts` و`apps/website/middleware.test.ts`؛ للبديل المحمي كذلك `features/auth/login-form.tsx` و`features/auth/login-form.test.tsx`، وللبديل العام `app/robots.ts` و/أو metadata ضمن layout خادمي مستقل (تحقق من قيود `'use client'` في صفحة confirm) مع اختبار noindex؛ `robots.ts:13` لا يمنع `/booking/confirm` اليوم. لا تعدّل `apps/backend/src/api/public/bookings.controller.ts` أو خدمات Moyasar أو إنشاء الحجز. تعديل `apps/website/middleware.ts` يمس بوابة auth، فلا ينفذ حتى يوافق مالك النطاق صراحة على السيناريو والاختبارات المستهدفة.

**المشكلة:** `payment-callback/page.tsx:30` ينشئ `/booking/confirm?bookingId=...`، لكن `middleware.ts:106-109` ينقل `pathname` فقط إلى login، ثم `confirm/page.tsx:27-30` يفترض الفشل عند غياب المعرف. للبديل المحمي فقط: عند التحويل للمسار المحمي، انقل *pathname + search الداخلي* بصورة آمنة إلى `redirect`، بالترميز عبر `URLSearchParams` لا concat خام لرابط خارجي. ابدأ باختبار محاكاة زيارة `/booking/confirm?bookingId=<UUID>&invoiceId=<UUID>` بلا كوكي، ثم login والعودة عبر redirect. حافظ على حماية `/account/*`، وقاعدة `sawa_local_signed_out`، والتحقق من redirect داخلي فقط في `features/auth/login-form.tsx:68-80`؛ لا تقرّب توقيع الكوكي أو تكشفه للعميل. احصر/نقّح مفاتيح الاستعلام الحساسة عند الحاجة ولا تحفظ معرّفات حجوزات في سجلات. اختبر طول الرابط وترميز `%`, `&`, `?` وquery متعدد، ولا تضف بارامترات غير ضرورية للمستخدم. في البديل المحمي، أصلح صراحةً `login-form.tsx:76-79`: إذا حضر `groupId` بجانب `redirect` يضيف الكود `?groupId=...` بعد رابط قد يحتوي `?bookingId=...` فينتج URL مشوهًا؛ استخدم تركيب URL محلي آمن مع إبقاء validate للـ relative path واختبار regression للحجز والباقات والدردشة. في البديل العام، هذا العيب مستقل يمكن تسجيله كمهمة منفصلة ولا تجعل C تتسع له بلا سبب. إن تبيّن أن `login-form` يحجب URL المشروع، يُراجع نطاق regex ضمن خطوة C فقط بعد اختبارات أمنية للـ open redirect.

**قرار منتج وأمان يجب حسمه قبل تنفيذ C (لا تُنفّذ البديلين معًا بالصدفة):** (1) إبقاء `/booking/confirm` خلف middleware مع إصلاح استعادة query هو أقل تغيير في حدود الوصول، لكنه قد يطالب العميل بتسجيل الدخول بعد العودة من البنك. (2) جعلها عامة يتسق مع endpoint حالة الحجز العام المخصص للتأكيد (`@Public()` وthrottle وUUID) ويمنح رؤية فورية للحالة عند انتهاء الجلسة، لكنه يغيّر سياسة الوصول إلى الصفحة. قيّم الصفحة كاملةً وما قد تعرضه مستقبلًا، التعرض إذا سُرّب UUID، throttling، الخصوصية، الروابط والفهرسة والتعامل مع `Referer`، واختبر 3DS في sandbox. للبديل العام أضف منع الفهرسة صراحةً عبر metadata/robots والاختبار، وحاجز مراجعة يمنع إضافة بيانات شخصية لصفحة الحالة العامة مستقبلًا؛ للبديل المحمي تحقق من أن `bookingId` في رابط `/login?redirect=...` لا يتسرب إلى logs/analytics أو Referer لطرف ثالث، وراجع سياسة referrer الفعلية (`apps/website/next.config.headers.test.ts:46` يتوقع `strict-origin-when-cross-origin`) قبل الادعاء بالأمان. اطلب موافقة مالك auth/payment الصريحة على أحد البديلين. إلى حين القرار، لا تغيّر `PROTECTED_PATHS` أو الحراس؛ البديل الأول ليس حلًا كاملًا لتجربة عميل يتعذر عليه الدخول.

**معايير القبول:**
- C1 (البديل 1 المحمي): مستخدم بلا كوكي أو مع `sawa_local_signed_out=1` يصل إلى login ويحمل `redirect=/booking/confirm?bookingId=...` بعد فك الترميز، ثم يعود إلى نفس معرف الحجز بعد نجاح الدخول. (البديل 2 العام): يبقى على تأكيد الحجز ويستطلع الحالة دون جلسة؛ روابط الحساب فقط تطلب الدخول عند الضغط عليها. اكتب اختبارات الفرع الذي يوافق عليه المالك، ولا تختبر قبول البديلين كسياسة واحدة.
- C2: كوكي حاضر وغير معلّم signed-out يمر من middleware إلى الصفحة (وصلاحية الجلسة الفعلية تبقى رهينة تحقق API/client)، وصفحة callback العامة لا تتطلب جلسة؛ نتيجة الدفع لا تعتمد على query `status` غير موثوق بل API الحالي.
- C3: غياب `bookingId` حقيقةً لا يزعم نجاحًا؛ وعند فقدان جلسة فقط لا يتحول موعد ناجح إلى رسالة «فشل الدفع» بسبب فقدان المعرف. المعرّف غير الصالح أو استجابة 400/404 أو polling منتهٍ لا تُفسَّر تلقائيًا كنجاح؛ تُختبر حالات انتظار/خطأ ورسالة إعادة المحاولة وفق سلوك الصفحة الحقيقي.
- C4: معلمات redirect من مصادر خارجية أو `//evil...`/backslash/control تبقى مرفوضة؛ لا تسقط المعاملات اللازمة لصفحات الحساب الأخرى أو تسجيل الباقات.
- C5: CSP والـ nonce ومطابقة middleware لا تتغير دون قصد؛ لا تعديل للـ JWT أو endpoint الدفع.
- C6 (البديل المحمي): حالة `groupId` بالتزامن مع `redirect` الذي يملك query لا تنتج `?` ثانية أو تضيع `bookingId`، ولا تتغير تكملة الحجز الجماعي والدردشة إذا عُدلت صياغة الرابط في login. (البديل العام): إضافة منع فهرسة تأكيد الحجز، واستمرار حراسة رابط الحساب وتقييد الصفحة بحالات غير شخصية.

**التحقق:**
```bash

pnpm --filter=@sawaa/website typecheck
pnpm --filter=@sawaa/website lint
```
إذا تعذر بناء staging مع Moyasar sandbox، لا تقول إن عودة 3DS حيًا نجحت. قبل قبول C شغّل مجموعة موقع الويب كاملة `pnpm --filter=@sawaa/website test` ثم `pnpm --filter=@sawaa/website build` إن توفرت متغيرات البناء الصحيحة؛ يُسجل تعذّر البناء بدل تجاوزه بصمت.

**تراجع/حد توقف:** إذا أدى تعديل redirect إلى loop أو تسريب هدف خارجي، استرجع middleware فقط؛ تبقى صفحة callback العامة كما كانت. لا تجعل endpoint حالة الحجز أوسع أو تضف التحقق إلى مسار دفع حساس كحل التفافي.

### F — احذف جلب مواعيد الحساب غير المستعمل دون تغيير سلوك القائمة

**الملفات:** `apps/website/themes/sawaa/pages/account-bookings.tsx` و`apps/website/features/auth/client-bookings-list.tsx`، اختبار `features/auth/client-bookings-list.test.tsx` واختبار Route/Server component عند الحاجة. لا تغير API ولا منطق التصفية/التقسيم في القائمة أو بيانات العميل.

**الحل الأقل مخاطرة:** أزل طلب `getMyBookingsApi` من server page، والـ props `initialBookings/initialTotal` التي لم تُستخدم؛ أبق `locale` وshell. لا تنقل الجلب إلى SSR «للتحسين» من دون نموذج آمن لتمرير كوكي الجلسة وتهيئة بيانات React Query مع المفتاح/الفلتر/pageSize الصحيح؛ SSR الحالي يضبط `credentials: 'include'` في طلب الخادم، وهذا وحده لا يثبت تمرير كوكي طلب المتصفح إلى fetch خادمي؛ افحص headers الفعلية قبل أي قرار مستقبلي باعتماد SSR مصدرًا للحقيقة. بعد الإزالة يظل `ClientBookingsList` يجلب `page=1, pageSize=50, tab=upcoming` ويعرض loading/error/empty، وتعمل التبويبات والتصفح. قرّر مصير query `page/pageSize` الوارد للـ route: حاليًا لا يتحكم بقائمة العميل؛ لا تدّعِ أنه pagination فعّال. أبق روابط الاستعلام موجودة لكن أزل قراءتها غير المستعملة داخل `account-bookings.tsx` في F؛ تغيير معنى روابط pagination متطلب مستقل.

**معايير القبول:** F1 لا يستدعي SSR endpoint الحجوزات إطلاقًا؛ F2 يبقى نمط جلب العميل كما كان قبل الإصلاح ولا يضاف طلب جديد عند أول mount (مع ملاحظة dev Strict Mode) مع ترشيح tab؛ F3 أي خطأ شبكة في العميل يعرض retry لا empty؛ F4 روابط `/account/bookings/[id]` والعودة والمزيد تعمل؛ F5 لا معلومات حساسة في HTML الأولي. **لا تعالج تعليق catch بإخفاء أخطاء إضافية؛ احذف السبب غير المستعمل.**

**الأوامر:**
```bash

pnpm --filter=@sawaa/website typecheck
pnpm --filter=@sawaa/website lint
```
أضف اختبارًا إلزاميًا للمكوّن الخادمي `SawaaAccountBookingsPage` بمُحاكاة `getMyBookingsApi` بحيث يفشل إذا استدعاه render، ويتحقق من وصول `locale` لقائمة العميل؛ عدّل اختبار القائمة الذي يمرر `initialBookings` لأن هذا الـ prop سيُحذف، واحتفظ بتوقع نتائج API والتصفح. لا تقارن عدد الشبكات في dev Strict Mode باختبار runtime للإنتاج دون ضبط البيئة. التراجع بإرجاع F فقط لا يغيّر مخطط قاعدة أو صلاحيات. قبل قبول F شغّل أيضًا `pnpm --filter=@sawaa/website test` للتحقق الكامل من الموقع بعد تغيير العقد الداخلي للـ props.

### D وE — تحقق تكاملي حي قبل قبول التغيير

**D الجوال:** محاكي/جهاز iOS وAndroid عند الإمكان: تثبيت نظيف واستعادة جلسة عميل، ضيف، staff، فتح `/home` العميق، رجوع بلا history من booking وpublic detail، logout ثم login/OTP، فتح إشعار appointment (مع id) ورجوع، واستكمال اختيار DIRECT/SERVICES مع الاحتفاظ بـ clinicId/serviceId. التقط نتيجة تبويبات الشريط وعدم loop. لا تُشغّل تطبيقًا جديدًا على جهاز المستخدم دون تنسيق؛ إذا تعذر الجهاز سجّل «وحدات/أنواع فقط؛ تجربة فعلية معلّقة». بعد كل PR للجوال اذكر ما اختُبر على محاكي وما اختُبر على جهاز حقيقي منفصلين. حدّث سجل الإصدار المؤرخ وREADME كما في `apps/mobile/CLAUDE.md:124-126` مع Git state والأوامر والمعرّفات المتاحة بلا أسرار.

**E الموقع:** بيئة محلية/اختبار منفصلة بعميل تجريبي ومعرف حجز تجريبي: callback مع `bookingId`, اختر «تابع في الموقع» في جلسة صالحة ثم منتهية؛ تحقق من رابط login والعودة والدفع المؤكد/معلّق/فشل حقيقي وretry. اختبر `/account/bookings` أول تحميل، filter وتصفح ومشكلة الشبكة، ثم تحقّق من زائر بلا صلاحية وmarker local signed out ومن روابط تسجيل الباقات. إجراء Sandbox Moyasar مستقل قبل أي ادعاء بصحة دفع حي. لا تنفّذ عمليات دفع حقيقية أو SMS بلا بيئة تجريبية وموافقة المالك. دوّن الإخفاق مع الخطوة/البيئة لا مع هوية مستفيد.

**حاجز نجاح:** لا يعلن «تم الإصلاح» على أساس وحدات خضراء فقط. يجب إظهار نتائج كل حالة فعلية أعلاه أو تسمية ما لم يُختبر، ووقف الترقية عند فشل تدفق جوهري. التحويلات security/payment تُراجع من مالك النطاق قبل نشرها، ولو كان التغيير سطرًا واحدًا.

### G — تنظيف معماري **بعد** تثبيت السلوك لا قبله

1. راجع تقرير URLs السبعة في Expo Router: `/home`, `/explore`, `/appointments`, `/chat`, `/profile`, `/video-call`, `/appointment/[id]`. لا تعِد تسمية أو تحذف مسارًا مستخدمًا في deep link أو إشعار. وثّق *المسار المؤهل بالمجموعة* المستعمل داخليًا، واختبر bare URLs ودور user على جهاز. alias الشاشات العامة يبقى حيث يلزم؛ يمكن اختزال `app/explore.tsx` و`(client)/(tabs)/explore.tsx` إلى shell صغير ومكوّن مشترك إذا زاد تكرار العرض، لا PR إجباري ما دام `ExploreDirectory` مشتركًا. chat فيه تحويل من `(client)/chat` إلى `(tabs)/chat` ثم home؛ اختصر سلسلة التحويل فقط بعد اختبار الروابط القديمة. راجع `records.tsx` غير المسجل كتَبويب ولا تنقله إلا مع حفظ رابط قديم.
2. راجع حراسة الموقع على أنها طبقتان مختلفتان: middleware hint سريع لا يثبت صحة JWT؛ `useCurrentClient`/API هما التحقق الحقيقي. `AuthGuard` داخل `account-packages` وشرط `AccountFeature` ليسا قابلين للاستبدال المتبادل بلا تغطية حالات `logout-pending`, network error وhydration (`account-feature.tsx:64-76,115-150`). لا تلمس الحراس أو تعرض تفاصيل حساب في SSR ما لم يثبت اختبار سلوك مكسور وموافقة مالك auth. أضف اختبار مصفوفة لا refactor شامل لمجرد التشابه.
3. لوحة الإدارة **خارج التنفيذ هنا**: `AuthGate` و`/login` يعيدان استخدام **نفس** `LoginForm`، فلا نسخ تنفيذ أصلًا. اكتفِ بتوثيق فرق عنوان URL كتساؤل منتج منفصل؛ لا تُغيّر ملفات `apps/dashboard` أو تبني عليها قبول هذه الخطة. عند تكليف مستقل لاحق يجري تحديد اختبارات auth وdashboard smoke بوثيقته الخاصة.
4. التشابه البصري بين تأكيد wizard و`/booking/confirm` لا يبرر دمجهما الآن: الأول نتيجة داخلية والثاني poll خارجي؛ يمكن استخراج مكوّن presentational مشترك إذا أثبتت اختبارات الحالات الأربع أن معانيها متطابقة. لا تغيّر منطق حالة الدفع نفسه لأجل تقليل الأسطر.

**مخرج G:** خريطة نهائية route→audience→guard→source UI→entry/deep link→test، مع قائمة alias مقصود/خلل مغلق/ديون مؤجلة، لا حذف مسارات أو نقل مالي غير مثبت.

## 3) استراتيجية الفروع والتسليم والتراجع

- عند طلب تنفيذ لاحق: ابدأ فرع مهمة من `develop` وفق `docs/operations/deployment-policy.md` واحفظ أي عمل قائم؛ يمكن العمل بالتوازي في worktrees منفصلة لـ B/C/F. لا commit/push/PR/merge/deploy لمجرد موافقة على الخطة أو طلب تنفيذ؛ سياسة النشر تفرق بين الإصلاح والنشر.
- اختر PR/تغييرًا صغيرًا لكل B وH وC وF، مع تجربة الرجوع إلى النسخة السابقة لكل نطاق. التراجع قبل النشر يختلف عن بعده: عكس تغيير الموقع في staging مع التحقق من revision، أما جوال موزع بالفعل فلا يتراجع بمجرد `git revert`؛ حدّد المرشح المثبّت والقناة وقدرة OTA الفعلية ثم، فقط بتفويض نشر منفصل وبعد تحقق التوافق، استخدم إصدار تصحيحي عبر القناة إن كانت مدعومة أو build جديدًا/TestFlight ومتجر بحسب `docs/mobile-app/runbook.md`. لا تعد بأن OTA ممكن قبل التحقق من قناته وruntimeVersion. لا Migration، ولا OpenAPI sync ما لم يتغير endpoint (والخطة لا تتضمن تغييره). إذا اتضح أن endpoint لا يفي بالعقد، أوقف هذه الخطة واطلب تعديل نطاق وموافقة auth/payment وتحديث OpenAPI/API client مع اختبار sandbox.
- تنشر staging فقط بعد أمر «انشر» صريح واستكمال مراجعات/اختبارات؛ «انشر للإنتاج» فقط بعد قبول المالك اليدوي لإصدار staging المحدد والتأكد من محتوى release. سجّل revision والبيئة ونتائج التحقق؛ لا تساوِ CI ناجحًا بنشر ناجح. rollback كودي فقط؛ لا قاعدة بيانات تمس.

## 4) مصفوفة قرار واضحة

| وضع التنفيذ | القرار |
|---|---|
| أول اختبار regression يفشل كما هو متوقع | نفذ أصغر تغيير يعيده للأخضر، ثم أعد المصفوفة كاملة |
| اختبار قديم أخضر لكنه لا يغطي الحالة | أضف اختبارًا يميّز المسار الجذري من tab shell أو URL مع query؛ لا تغيّر الحارس بالحدس |
| جلسة مؤقتة/منتهية ترجع من 3DS | C يحفظ المعرف عبر login؛ تغيير ظهور confirm للضيف **قرار أمني منفصل** |
| فشل حي للدفع أو حساب عميل بعد تعديل redirect | أوقف الدمج/النشر، أعد C فقط، احتفظ بالأدلة دون بيانات مستفيد |
| تعذر محاكي أو sandbox | أكمل تحققًا آليًا فقط، واترك حالة التحقق الحي مفتوحة؛ لا تدّعِ جاهزية إصدار |
| رغبة لاحقة «حذف كل الصفحات المكررة» | اعرض خريطة alias والاستخدام قبل أي حذف؛ حافظ على روابط التوافق وتكملة الحجز |

**تعريف الاكتمال:** معايير B وH وC وF مثبتة باختبارات حمراء→خضراء، typecheck/lint والتغطية الكاملة الخاصة بالجوال أو توثيق قيدها، تحقق حي D/E أو إعلان عدم إجرائه بوضوح، اعتماد مالك auth/payment قبل تعديل حدوده، توثيق إصدار الجوال، ثم تقرير نهائي يذكر الفرق بين خلل تم إصلاحه وبين ازدواجية مقصودة أو قرار مؤجل. لا تُعتبر إتاحة نشر staging أو الإنتاج ضمن اكتمال الإصلاح المحلي.

## 5) بروتوكول تعديل الخطة لاحقًا

عند اكتشاف دليل يخالف افتراضًا، سجّل الملف/السطر والتجربة، سمِّ المعيار المتأثر، وقسّم أو عدّل *الخطوة التي لم تبدأ* فقط؛ لا تنسخ إصلاحات مسبقة إلى مسار جديد. أي قرار يجعل صفحة محمية عامة، يغيّر حارسًا/كوكيًا أو يغيّر API دفع يحتاج موافقة مالك النطاق وعقد قبول جديد واختبار sandbox منفصل. الخطوات الاختيارية G لا تؤخر عيوب B/C/H/F، لكنها لا تُنفّذ تلقائيًا عند إنجازها.
