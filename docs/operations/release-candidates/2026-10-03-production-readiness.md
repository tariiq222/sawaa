## نقاط تمنع الاعتماد الحالي

### 1. سباق جديد في إعادة التسجيل — P2، دليل ثابت

`apps/backend/src/modules/identity/register-mobile-user/register-mobile-user.handler.ts:64-76` يقرأ أن الحساب غير مفعّل، ثم يحدّثه بالمعرّف فقط. إذا أكمل `verify-mobile-otp.handler.ts:58-64,134-140` التفعيل بين القراءة والكتابة، يستطيع طلب إعادة التسجيل تعديل الاسم والبريد بعد التفعيل دون إثبات امتلاك الهاتف، وقد يختلف User عن Client المرتبط. قفل OTP لا يمنع كتابة غير مشروطة تنتظر انتهاء القفل. لا يُدّعى الاستيلاء على الحساب.

المطلوب: إصلاح محدود يربط الكتابة بشرط أن الحساب ما زال مؤهلًا لإعادة التسجيل، أو قفل وإعادة تحقق متوافقان، مع اختبار التداخل. لم يُعدّل هذا المسار لأنه من نطاق المصادقة الذي يتطلب موافقة المالك الصريحة وفق AGENTS.md.

### 2. سياسة الجلسات القديمة غير محسومة — خطر قائم وليس تراجعًا جديدًا

Migration `20261001200000_add_refresh_token_source` تترك الصفوف القديمة بمصدر NULL. `apps/backend/src/api/public/auth.controller.ts:170-192` يرفض MOBILE فقط، ثم يصدر بديلًا بمصدر DASHBOARD الافتراضي في `shared/token.service.ts:55,81-87`. لذلك يمكن لتوكن موظف جوال قديم صالح أن يستمر عبر مسار تجديد اللوحة دون حارس أهلية الجوال، وقد تتجدد صلاحيته بعد التحويل. هذا تجاوز سابق لم تغلقه الترقية لجميع الجلسات القديمة؛ يتطلب وجود توكن قديم صالح، ولم تُفحص توكنات العملاء أو تُكشف قيمها.

المطلوب: قرار صريح لكيفية التعامل مع الجلسات مجهولة المصدر، ثم اختبار جلسات اللوحة القديمة والجوال القديم وحالة 2FA. لا يجوز إلغاء جميع الجلسات أو نسبتها لقناة معينة تلقائيًا. لا يصح اعتماد وعد «لن يُطلب تسجيل الدخول مجددًا» لجميع مستخدمي التطبيق؛ الكود يرفض بعض جلسات User CLIENT القديمة ويحتاج مسار استعادة بالـOTP.

### 3. تحقق Moyasar وsmoke يدوي ما زال مطلوبًا

[PR #102](https://github.com/tariiq222/sawaa/pull/102) يذكر صراحة أن sandbox لم يُنفذ. اختبارات الاسترداد المحلية تمر، لكنها تستخدم mocks. لم نجد ضمن الأدلة المراجعة قبولًا أحدث على المرشّح يغلق هذا الشرط.

يلزم على بيئة اختبار مسموح لها بالاتصال بمزوّد الاختبار: أول استرداد جزئي/كامل، رفض الاسترداد الثاني دون POST ثانٍ للمزوّد، حالة نتيجة المزوّد غير المؤكدة والمصالحة، واختبار لوحة الإدارة. لم يُرسل دفع أو SMS أو طلب مزوّد في هذه المراجعة. الاستيج شبكة Docker داخلية `Internal=true`؛ لا تفتح اتصالًا خارجيًا قبل إثبات استخدام مزوّدين وبيانات اختبار. اشتراك مفتاح تشفير الإعدادات بين البيئتين لا يثبت وحده تطابق حسابات المزوّدين، ولم يُغيّر المفتاح.

## ترتيب الإغلاق ثم الترقية

1. اعتماد نطاق إصلاح المصادقة المحدد أعلاه، وتنفيذه في فرع معزول باختبارات السباق والجلسات القديمة؛ لا تعديل تلقائي لبيانات الإنتاج.
2. نشر الإصلاح على الاستيج بمسار PR والفحوص، وتحديث SHA المرشّح؛ أي تغيير يلغي قبول النسخة السابقة وحدها.
3. إغلاق sandbox وdashboard smoke، ثم قبول المالك للدخول والحجز وإعادة الجدولة والدفع والاسترداد وتوافق نسخة الجوال المنشورة. التطبيق نفسه يُنشر عبر TestFlight، لكن API الإنتاج يؤثر فيه.
4. توثيق migration provenance وتجربة الاستعادة/الترقية والنسخة الاحتياطية المطلوبة وخطة الرجوع بالصور السابقة.
5. فقط بعد أمر المالك الصريح «انشر للإنتاج»: إنشاء PR من develop إلى main، فحوص على نفس المحتوى، مراجعة تحرّك الفرعين، ودمج يحفظ ancestry دون squash لترقية الفرعين الطويلين. لا cherry-pick جماعي ولا إعادة كتابة التاريخ.
6. مراقبة النشر الآلي، مطابقة SHA الفعلي، صحة الخدمات ومسارات العمل، ثم إيصال نشر وفق `docs/operations/deployments/README.md`. عند فشل بوابة نتوقف؛ لا تجاوز للفحوص.
