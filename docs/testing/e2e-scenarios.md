# سيناريوهات سواء لاختبارات الرحلات

تاريخ إعداد القائمة: 2026-10-08. هذه قائمة تنفيذ ومعايير قبول، وليست شهادة نجاح أو تغطية مكتملة. توضع السيناريوهات قبل كتابة الاختبارات وتُراجع عند تغيير مسار المنتج. الأولوية للرحلات التي تمس الحجز والمال والهوية، مع خطوات واجهة مختلفة للموقع والتطبيق وتأكيدات أعمال مشتركة.

## المرحلة الأولى المعتمدة

## الهوية والحالات السلبية المصاحبة

- SW-A01 / P0: دخول العميل بكلمة مرور صحيحة، ثم فتح بياناته المحمية بهويته الصحيحة؛ كلمة مرور خاطئة لا تنشئ جلسة.
- SW-A02 / P0: عميل ثانٍ لا يستطيع قراءة حجز الأول أو استخدام رصيد باقته.
- SW-B04 / P0: سياق عيادة قديم أو ممارس لا يقدم الخدمة المختارة يُرفض؛ لا توسيع تلقائي إلى خدماته الأخرى.
- SW-B05 / P0: متنافسان على الموعد نفسه لا يحصلان على حجزين متعارضين.
- SW-K02 / P1: رصيد منتهي/غير مؤهل لا يُتاح للحجز، وإلغاء الحجز يعيد المتاح وفق سياسة الرصيد.
- SW-R01 / P1: موظف الاستقبال والممارس والمدير يرون ما تسمح به أدوارهم؛ لا تُغيّر الصلاحيات لإرضاء الاختبار.

## عقد البيئة والبيانات قبل أتمتة الحجز

1. قاعدة Postgres اختبار قابلة للاستبدال، وRedis/موارد تشغيل معزولة. يبدأ `create-real-e2e-app.ts` فقط عبر `REAL_E2E_DATABASE_URL` ويرفض الرجوع إلى DATABASE_URL؛ نتبع هذا النمط.
2. أسماء ومعرّفات صناعية تخص التشغيل، ووقت/منطقة زمنية `Asia/Riyadh`، وموعد مستقبل محدد، ومبلغ موجب معلوم بالهللات. لا استخدام لعملاء حقيقيين.
3. كتالوج يغطي DIRECT وSERVICES وSERVICE_GROUP وخدمة غير نشطة وداخلية مفقودة وممارسًا يقدم عيادتين؛ لا استنتاج من أسماء الأقسام.
4. ضريبة سواء صفر. لا ننسخ بذور الاختبارات القديمة التي تضبط `OrganizationSettings.vatRate=0.15`. إعدادات المركز مفردة ومشتركة؛ لا تعديل متزامن لها من أكثر من اختبار.
5. تنظيف البيانات الصناعية يقتصر على موارد التشغيل المعزولة. لا reset أو seed أو حذف على قاعدة مشتركة أو إنتاجية.
6. لا endpoints للاختبار داخل المنتج، ولا تجاوز guard/token/CASL، ولا تغيير تشفير أو مفاتيح أو AAD.

## ما يشترك بين المنصات وما يختلف

المشترك: العميل، معرّف الحجز، الخدمة، الممارس، الموعد، المبلغ بالهللات، العملة، الحالة، معرّف الفاتورة/الدفع والرصيد. نقارن القيم المتفق عليها بعد كل مرحلة، ولا نكتفي برسالة النجاح.

المختلف: الموقع يستخدم `/booking` وجلسة cookies وتحويل الدفع؛ التطبيق يستخدم مسارات Expo وسياق العيادة وجلسة native وواجهة الدفع الأصلية. نكتب محرك خطوات لكل سطح مع معايير أعمال واحدة، ولا نفترض أن ملف UI واحد يصلح حرفيًا للجميع.

## أدلة القبول وحدودها

- API وقاعدة الاختبار: إثبات الحالة والمعرفات والمبالغ والتزامن، دون إثبات وصول الرسائل أو تحصيل المزود الحقيقي.
- المتصفح/المحاكي: إثبات خطوات الواجهة وربطها بالباك داخل البيئة المختبرة.
- Moyasar Sandbox: نجاح وفشل و3DS وwebhook حقيقي منفصل عن الاختبارات ذات الاستجابة المضبوطة.
- جهاز iPhone فعلي: Apple Pay والروابط العميقة والإشعارات واستئناف التطبيق حسب قدرات الجهاز؛ نجاح Simulator لا يغطيها.
- SMS/Email/FCM: إنشاء طلب أو حدث outbox لا يثبت التسليم؛ اختبار المزود يحتاج تأكيد وصول فعلي إلى حساب/جهاز اختبار.
- لكل تشغيل: نسخة الكود، البيئة، منصة الجهاز، معرفات بيانات الاختبار، النتائج والتخطيات وأسبابها، ومسارات الأدلة؛ بلا أسرار أو بيانات عملاء.

اعتماد أي سيناريو يتطلب نجاح تأكيداته المحددة. فشل التجهيز أو غياب الحساب/المزود يعني «محجوب/غير مختبر»، لا «ناجح».

## تشغيل المرحلة الثانية

أضيفت بيئة بيانات مستقلة وحواجز تمنع الرجوع إلى قاعدة مشتركة. خطوات التشغيل في [الدليل المحلي](e2e-local-runbook.md). دليل المرحلة الأولى أعلاه يخص تشغيله السابق؛ نتائج المرحلة الثانية تُسجّل منفصلة ولا تحول السيناريوهات المخططة إلى تغطية تلقائيًا.

تنفيذ SW-P01 الحالي يخص Native API مع بطاقة Moyasar Sandbox حقيقية وتكرار reconcile. لا يثبت webhook أو checkout الموقع المستضاف أو واجهة SDK داخل التطبيق. تبقى DIRECT، وعزل هوية عميل ثانٍ، وتنافس المواعيد، وفشل الدفع/انتهاء الحجز، والباقات والإلغاء سيناريوهات تالية.
