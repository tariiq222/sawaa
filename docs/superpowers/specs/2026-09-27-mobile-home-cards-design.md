## المطلوب والشكل المقترح

إضافة شريط كروت بين شعار مركز سواء والتحية في الرئيسية، للزائر والعميل المسجل. بتوجيه المستخدم اللاحق، يظهر كرت واحد كامل دون أطراف الكروت المجاورة أو سكرول حر. السحب يبدّل الكرت بتلاشي خفيف وانزلاق قصير في نحو ربع ثانية، مع نقاط للتنقل. اتجاه الانتقال يتبع اللغة، وتقليل الحركة يلغي الأنيميشن. لا تشغيل تلقائي في الإصدار الأول.

كل كرت مستطيل بعرض أغلب الشاشة، بإطار زجاجي وصورة اختيارية وعنوان ووصف قصير اختياري. بتوجيه المستخدم اللاحق في 2026-09-27، تملأ الصورة كامل خلفية الكرت بأسلوب cover مع قص الأطراف عند اختلاف الأبعاد، ويظهر النص فوقها بتدرّج خفيف جدًا وظل بسيط للنص؛ رفض المستخدم التعتيم القوي. الكرت بلا صورة أو عند فشلها يعود للسطح الزجاجي والنص بألوان الثيم. يظل ترتيب بقية الرئيسية كما هو. يمكن عرض كرت واحد، ويختفي القسم دون فراغ عندما لا توجد كروت منشورة. هذه افتراضات تصميمية مقترحة، إضافة إلى موضع الشريط والتحكم الإداري اللذين طلبهما المستخدم.

## التحكم في الأدمن

تبويب «كروت التطبيق» في الإعدادات، يتضمن قائمة مرتبة ومعاينة للكرت. يستطيع صاحب صلاحية تعديل الإعدادات إضافة الكرت وتعديله، رفع صورته أو إزالتها، تغيير ترتيبه، وإظهاره أو إخفاءه. لا حاجة للحذف الدائم؛ الإخفاء يحتفظ بالمحتوى لإعادة استخدامه.

الحقول: العنوان بالعربية (مطلوب، حتى 100 حرف)، العنوان بالإنجليزية (اختياري)، الوصف باللغتين (اختياري، حتى 240 حرفًا)، صورة اختيارية من مكتبة الملفات، وترتيب العرض وحالة النشر. عند غياب الإنجليزية يُعرض النص العربي. يلزم وصف بديل للصورة إذا كانت تحمل معلومة إضافية.

وجهة النقر اختيارية من قائمة وجهات داخلية محددة: العيادات، الخدمات، المختصون، الباقات، البرامج. الكرت بلا وجهة يعرض المحتوى فقط ولا يبدو كزر. لا روابط خارجية ولا إدخال مسارات حرة في الإصدار الأول. ربط كرت بعيادة أو خدمة بعينها يمكن إضافته لاحقًا إن طُلب.

## البدائل والقرار المقترح

1. **كيان مخصص لكروت الجوال — موصى به:** تخزين منظم، تحقق من الحقول، قائمة عامة لا تكشف المسودات، وتوسعة مستقلة عن إعدادات الهوية.
2. حقل JSON داخل إعدادات المركز: ملفات أقل، لكن تعديل قائمة كاملة يجعل تعارض تعديلات الموظفين والتحقق من عناصرها أصعب.
3. إعادة بناء CMS شامل: يتجاوز الحاجة الحالية. فحص المستودع أظهر أن CMS السابق أُزيل، وملف `content.prisma` يوثق ذلك.

## عقد التنفيذ

- نموذج `MobileHomeCard` جديد في Prisma مع migration إضافية فقط: UUID، حقول المحتوى، `imageFileId` اختياري، `destination` enum اختياري، `sortOrder`، `isPublished` افتراضيًا false، ووقتا الإنشاء والتعديل. لا تعديل لبيانات الكتالوج أو الحجوزات.
- API إدارة تحت `/dashboard/mobile-home-cards`: قراءة، إنشاء، تعديل. إعادة استخدام `JwtGuard` و`CaslGuard` وصلاحيتي `read Setting` و`update Setting` القائمتين دون تغيير قواعد الصلاحيات.
- API عام `/public/mobile-home-cards` يعيد الكروت المنشورة فقط، بترتيب `sortOrder` ثم `id` ثابت، وبالحقول اللازمة للعرض فقط. تحويل مرجع الصورة إلى URL عبر نظام الملفات الموجود؛ لا تخزين رابط موقع مؤقت في قاعدة البيانات. يجب تأكيد سياسة الصور العامة قبل التنفيذ كي لا تُتاح ملفات خاصة.
- ترتيب الكروت بتحريك العنصر للأعلى أو للأسفل في الأدمن، وحفظ الترتيب في طلب ذري يتحقق من المعرفات. عند تعارض تعديلين يُرفض الطلب القديم عبر شرط `updatedAt` وتُطلب إعادة تحميل القائمة.
- تعريف DTO موثق وملفات AR/EN متطابقة. تحديث OpenAPI من خادم هذا الفرع وتوليد أنواع الأدمن. تحديث العميل المكتوب يدويًا فقط إذا كان مستهلكًا لهذا العقد.
- الجوال: service ثم query hook ثم `HomeCardsCarousel` مستقل يُدرج بعد `HomeTopBar`. استخدام `Glass` لعرض كرت كامل واحد في المرة كما طلب المستخدم لاحقًا، مع إيماءة تبديل أفقية ونقاط تنقل. إعادة الجلب عند تحديث الرئيسية؛ عند فشل الشبكة تبقى البيانات المحفوظة إن وجدت، وإلا يختفي القسم. فشل الصورة يعرض النص دون انهيار.
