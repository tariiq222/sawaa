# سلامة تدفقات المواعيد والدفع والباقات ووضوحها في الداشبورد

**التاريخ:** 2026-08-31
**الحالة:** تصميم معتمد مبدئيًا — بانتظار مراجعة المواصفات المكتوبة
**النطاق:** Backend + Dashboard + Website + Mobile + E2E
**الأولوية:** سلامة مالية ووضوح تشغيلي قبل التحسينات الشكلية

## الهدف

توحيد القواعد المشتركة للمواعيد العادية، والمواعيد المدفوعة من رصيد باقة،
والتسجيل في البرامج الجماعية، مع إبقاء الاختلافات الضرورية لكل نوع. يجب أن
تكون دورة الدفع ذرّية وقابلة لإعادة المحاولة بلا تحصيل أو خصم مزدوج، وأن تعرض
الداشبورد بوضوح أين توجد تعريفات الباقات ومشتريات العملاء، وهل الموعد مدفوع
بفاتورة أم محسوب من رصيد باقة.

## المصطلح المالي المعتمد

- الموعد العادي يُسدَّد عن طريق فاتورة ودفعة أو أكثر، أو يبقى للدفع في المركز.
- موعد الباقة **ليس خصمًا سعريًا على الموعد**. هو جلسة مدفوعة مسبقًا ضمن شراء
  باقة؛ لذلك يكون سعر الموعد التشغيلي صفرًا ويرتبط بـ `PackageCreditUsage`.
- الخصم يوجد عند شراء الباقة نفسها فقط، ويُجمَّد ضمن لقطة سعر الشراء.
- البرنامج الجماعي له تسجيل ومقعد، وقد تكون له فاتورة؛ نجاح إنشاء التسجيل لا
  يعني نجاح الدفع.
- في الواجهة نستخدم «محسوب من باقة» و«مدفوع مسبقًا» بدل «خصم باقة».

## المبادئ المشتركة لكل التدفقات

1. **معاملة واحدة للحالة الداخلية:** لا تعاد استجابة نجاح إلا بعد تثبيت الحجز
   أو التسجيل، والفاتورة/الدفع أو حركة رصيد الباقة، وسجل التدقيق اللازم.
2. **إعادة آمنة:** لكل عملية مالية أو شراء مفتاح idempotency ثابت، وتعيد
   المحاولة النتيجة السابقة بدل إنشاء حركة ثانية.
3. **قفل المصدر المالي:** قفل الفاتورة قبل احتساب المتبقي، وقفل رصيد الباقة قبل
   خصمه، وقفل البرنامج قبل حجز أو تحرير مقعد.
4. **حالة واحدة حاكمة:** لا يُستنتج النجاح من الواجهة. يعيد الباكند نتيجة صريحة
   تشمل حالة الموعد ومصدر السداد والخطوة التالية.
5. **أحداث ما بعد المعاملة لا تقلب النجاح إلى 500:** الحدث الاختياري الذي لا
   يملك مستهلكًا لا يفشل الطلب بعد تثبيت البيانات. الآثار الجانبية المطلوبة
   تُكتب في outbox داخل المعاملة وتُعاد محاولتها خارجها.
6. **لا دفع لموعد غير قابل للسداد:** الموعد الملغي/المنتهي/المسترد لا يقبل
   تحصيلاً جديدًا، وتصبح فاتورته غير قابلة للتحصيل بحسب السياسة المعتمدة.

## نموذج القراءة الموحّد للحجز

تُغنى استجابات قائمة وتفاصيل المواعيد بحقل مشتق لا يغيّر جداول الحجز:

```ts
type BookingFunding =
  | {
      kind: 'PACKAGE_CREDIT'
      packageId: string
      packageNameAr: string
      packageNameEn: string | null
      purchaseId: string
      creditId: string
      usageId: string
      totalQuantity: number
      usedQuantity: number
      remainingQuantity: number
    }
  | {
      kind: 'INVOICE'
      invoiceId: string
      status: InvoiceStatus
      total: number
      paid: number
      outstanding: number
      paymentMode: 'ONLINE' | 'AT_CLINIC' | 'MANUAL' | null
    }
  | {
      kind: 'NO_CHARGE'
      reason: 'FREE_SERVICE' | 'ADMINISTRATIVE' | null
    }
  | null
```

هذا الحقل read model فقط؛ مصدر الحقيقة يبقى `Booking.packageCreditId` مع
`PackageCreditUsage` أو الفاتورة المرتبطة بالموعد. تُستخدم نفس البنية في list
وdetail حتى لا تعرض الصفحات معلومات متعارضة.

## 1. إصلاح الأحداث وحدود المعاملة

### المشكلة

توجد عمليات تثبّت بياناتها ثم تستدعي أحداثًا مثل
`finance.invoice.created` و`bookings.booking.cancel_rejected` و
`bookings.program.min_reached`. عدم وجود مستهلك مسجل قد يرمي خطأ بعد نجاح
المعاملة، فيرى المستخدم 500 ويعيد العملية رغم أن البيانات أُنشئت بالفعل.

### التصميم

- يبقى `EventBusService.publish()` صارمًا للأحداث التي تتطلب مستهلكًا.
- تضاف دلالة صريحة للأحداث الرصدية/الاختيارية، مثل `publishOptional()`، وتكون
  عدم وجود مستهلك فيها نتيجة سليمة ومسجلة في debug telemetry.
- كل أثر مطلوب مثل إشعار مالي أو رسالة لا يجوز فقدها يُكتب في outbox داخل
  المعاملة ويُنشر لاحقًا.
- تُراجع الاستدعاءات الثلاثة المكتشفة وتصنف بحسب وجود أثر مطلوب فعلي، ولا تضاف
  مستهلكات no-op فقط لإسكات الخطأ.
- اختبار تكاملي يثبت أن العملية تعيد 2xx مرة واحدة، وأن إعادة الطلب لا تنشئ
  فاتورة/حجزًا ثانيًا حتى لو لم يوجد مستهلك اختياري.

## 2. سلامة التحصيل والفواتير والاسترداد

### التحصيل اليدوي والمتزامن

- ينفذ `ProcessPaymentHandler` داخل transaction ويقفل صف الفاتورة بـ
  `SELECT ... FOR UPDATE` قبل قراءة مجموع الدفعات المكتملة.
- يعاد احتساب `outstanding` بعد القفل، ثم يطبق قيد `amount <= outstanding`.
- القفل هو الحماية الأساسية حتى لو وصل طلبان بمفتاحين مختلفين؛ idempotency
  يحمي إعادة نفس الطلب فقط.
- تُرفض الفواتير التابعة لموعد بحالة لا تسمح بالدفع.

### العربون والرصيد المتبقي

- يسمح بدء الدفع الإلكتروني للموعد ذي الحالة `DEPOSIT_PAID` لتسوية المتبقي.
- قيمة طلب التحويل البنكي تُقارن بالمبلغ المطلوب حاليًا: العربون أو كامل
  المتبقي، لا بإجمالي الفاتورة دائمًا.
- نفس helper يحكم dashboard وwebsite وmobile لتجنب اختلاف السياسة.

### محاولات Moyasar

- تُنشأ محاولة دفع داخلية بحالة `INITIATING` ومفتاح فريد قبل الاتصال بالبوابة.
- تُحفظ هوية البوابة وتنتقل المحاولة إلى `PENDING/COMPLETED/FAILED` دون إنشاء
  محاولة جديدة عند إعادة نفس الطلب.
- عند انقطاع غير محسوم بعد الاتصال، تكون الحالة `REQUIRES_RECONCILIATION` ولا
  يُعاد الخصم تلقائيًا حتى تُستعلم البوابة أو يعالج webhook المحاولة.
- يعتمد التنفيذ النهائي على ما تدعمه وثائق Moyasar الرسمية الحالية من مفاتيح
  idempotency والاستعلام؛ يلزم إثبات sandbox ولا يكفي mock لـ `fetch`.

### الاسترداد متعدد الدفعات

- يحسب refundable balance على مستوى الفاتورة وكل دفعاتها المكتملة، لا على آخر
  دفعة فقط.
- تُخصص قيمة الاسترداد على دفعة أو أكثر ممن تملك رصيدًا قابلًا للاسترداد، مع
  منع تجاوز إجمالي المحصل ناقص المسترد سابقًا.
- كل allocation موثقة وقابلة لإعادة المحاولة بنفس المفتاح.

## 3. شراء الباقة وإصدار الرصيد

### البيع اليدوي من الداشبورد

- أمر بيع واحد يثبت لقطة تعريف الباقة وبنودها وأسعارها، وينشئ الشراء والفاتورة
  والدفعة اليدوية والدلاء، ثم ينشط الشراء داخل transaction واحدة.
- إذا فشل تسجيل الدفع لا يبقى شراء `ACTIVE` أو رصيد صالح بلا تحصيل.
- يقبل الأمر `idempotencyKey` فريدًا، وإعادة الإرسال تعيد نفس الشراء.

### الشراء الذاتي

- أول طلب ينشئ شراء `PENDING` واحدًا وفاتورة ومحاولة دفع واحدة باستخدام مفتاح
  شراء فريد؛ قيد فريد في قاعدة البيانات يمنع سباق طلبي init.
- تُحفظ لقطة كاملة لكل بند وقت init: الخدمة، المعالج، المدة، الكميات، سعر
  الوحدة، والاسم/القيم المالية المطلوبة للتدقيق.
- عند webhook الناجح تُصدر الدلاء من اللقطة المجمدة، ولا يعاد قراءة تعريف
  الباقة الحالي. تعديل الباقة بعد بدء الدفع لا يغيّر ما اشتراه العميل.
- الانتقال `PENDING -> ACTIVE` يحدث مرة واحدة فقط وبقفل الشراء.

### خصم الرصيد وإرجاعه

- `BookFromCreditHandler` يقفل دلو الرصيد، يعيد التحقق من أن الشراء `ACTIVE`
  ومن المطابقة (خدمة + معالج + مدة)، ثم ينشئ الموعد وحركة `CONSUMED` ويزيد
  `usedQuantity` داخل المعاملة نفسها.
- عند التعدد يستخدم FIFO ثابتًا (`purchase.createdAt`, ثم `credit.createdAt`,
  ثم `id`) لضمان نتيجة قابلة للتفسير.
- الإلغاء وno-show والانتهاء يعيد الحركة مرة واحدة فقط إلى `RETURNED` وينقص
  المستخدم، والاستعادة تعيد استهلاكها فقط إن بقي الرصيد صالحًا.
- تعرض النتيجة `funding.kind = PACKAGE_CREDIT` مباشرة بعد الإنشاء.

### استرداد شراء الباقة

- الاسترداد الجزئي المالي لا يلغي الرصيد تلقائيًا؛ يبقى موثقًا كمبلغ مسترد مع
  بقاء حالة الشراء النشطة ما دام هناك رصيد، ويظهر تحذير تشغيلي واضح.
- الاسترداد الكامل يرفض إذا وجدت مواعيد مستقبلية فعالة محسوبة من الشراء،
  ويعيد قائمة معرفاتها كي يلغيها الموظف صراحة أولًا. لا تُلغى مواعيد العميل
  بصمت.
- بعد عدم وجود مواعيد فعالة، يقفل الشراء ودلاءه، يثبت الاسترداد، ويحوّل الحالة
  إلى `REFUNDED` ويمنع أي استهلاك لاحق.

## 4. البرامج الجماعية

- التسجيل، حجز المقعد، وإنشاء الفاتورة تتم كعملية منسقة وحالة التسجيل تبيّن
  هل الدفع مطلوب.
- `ProgramEnrollment` هو مصدر حقيقة المقعد؛ كل إلغاء أو استرداد لحجز جماعي
  يحدّث التسجيل وعدد المقاعد داخل transaction واحدة.
- الإلغاء والتسجيل يقفلان صف البرنامج أو يستخدمان تحديثًا شرطيًا ذريًا واحدًا؛
  لا يمكن تجاوز السعة أو تحرير المقعد مرتين.
- استعادة no-show لا تؤكد الموعد إذا لم يعد المقعد متاحًا.
- الجوال لا يعرض نجاحًا نهائيًا لبرنامج مدفوع؛ يستقبل `invoiceId` و
  `nextAction: PAY` وينتقل لمسار الدفع، ثم يؤكد نجاح التسجيل بعد الحالة
  النهائية.
- سياسة إلغاء البرنامج تبقى «استرداد يدوي» كما هي حاليًا، لكن الداشبورد يعرض
  عدد المبالغ التي تحتاج معالجة ولا يوحي بأنها استردت تلقائيًا.

## 5. توحيد عقود website وmobile

- يطابق DTO إنشاء الموعد الحقول التي ترسلها التطبيقات، ومنها `deliveryType`،
  أو تزال الحقول غير المقبولة من العميل وفق عقد واحد موثق. الاختيار المعتمد:
  قبول `deliveryType` والتحقق منه لأنه جزء فعلي من الحجز.
- توحّد طريقة إلغاء العميل على `PATCH` في api-client والويب والجوال، وتستخدم
  `ClientCancelBookingHandler` حتى تطبق نافذة وسياسة العميل نفسها.
- كل نتيجة إنشاء تعيد `bookingId`, `status`, `funding`, `invoiceId?`,
  `nextAction` ولا تعتمد التطبيقات على تخمين وجود الدفع.
- تحدّث OpenAPI snapshot و`packages/api-client` اليدوي والتطبيقات في نفس
  التغيير.

## 6. تنظيم الداشبورد المعتمد

### مركز الباقات `/packages`

يبقى عنصر «الباقات» في القائمة الرئيسية، لكن الصفحة تصبح مركزًا بتبويبين:

1. **تعريفات الباقات:** القائمة الحالية للإنشاء والتعديل والأرشفة، مع السعر
   والخصم والجمهور والحالة.
2. **مشتريات العملاء:** جدول عالمي قابل للبحث والتصفية باسم العميل، الباقة،
   الحالة، تاريخ الشراء، المبلغ، المستخدم/المتبقي، ومصدر الدفع. يفتح الصف
   تفاصيل الشراء وحركات الرصيد والمواعيد المرتبطة.

يضاف endpoint paginated لمشتريات الباقات على مستوى المركز بدل تحميل ملفات
العملاء فرديًا. الصلاحيات تتبع finance/package permissions الموجودة ولا توسع
الوصول.

### ملف العميل

يبقى قسم «الباقات والأرصدة» داخل ملف العميل للسياق التشغيلي السريع. يعرض:

- بطاقة لكل شراء: اسم الباقة، حالتها، المدفوع، تاريخ الشراء.
- دلاء الرصيد: الخدمة، الممارس، المدة، `المتبقي / الإجمالي`.
- سجل الحركات: استهلاك/إرجاع مع رابط الموعد.
- إجراءات البيع، الحجز من الرصيد، النقل، والاسترداد حسب الصلاحية والحالة.

### قائمة المواعيد

- يظهر badge واضح «من باقة» بجوار حالة الدفع، وتحته اسم الباقة.
- السعر لا يعرض وحده كـ `0` بما يوحي بأن الموعد مجاني؛ يعرض «مدفوع مسبقًا».
- يتيح الفلتر `مصدر السداد`: باقة / فاتورة / بلا رسوم.
- لا تزدحم بقية أعمدة الجدول؛ التفاصيل الموسعة تبقى في sheet.

### تفاصيل الموعد

تضاف بطاقة «مصدر السداد»:

- للباقة: اسم الباقة، رقم الشراء، الخدمة/الممارس/المدة المثبتة، الحركة، ورصيد
  الدلو بعد هذه الحركة مع روابط ملف العميل وتفاصيل الشراء.
- للفاتورة: الإجمالي، المحصل، المتبقي، الحالة وطريقة الدفع.
- تعرض timeline لحركة الاستهلاك والإرجاع حتى يكون سبب الرصيد قابلًا للتدقيق.

### قواعد العرض

- كل النصوص عربية/إنجليزية متوازية عبر i18n.
- badges والألوان من design tokens ولا تستخدم ألوانًا حرفية.
- RTL باستخدام الخصائص المنطقية.
- loading/empty/error states لكل تبويب، والـ URL يحتفظ بالتبويب والفلاتر.
- لا تكرر منطق اشتقاق مصدر السداد في المكونات؛ mapper/hook واحد يستهلك
  `BookingFunding`.

## 7. ترتيب التنفيذ

### المرحلة A — الحواجز المالية والأحداث

إصلاح فشل الأحداث بعد commit، قفل الفاتورة، منع دفع الحالات الملغاة،
idempotency، العربون/المتبقي، والاسترداد متعدد الدفعات.

### المرحلة B — دورة حياة الباقات والجماعي والعقود

ذرية البيع اليدوي، snapshot وسباق الشراء الذاتي، استرداد الباقات، اتساق مقاعد
البرامج، وعقود website/mobile.

### المرحلة C — read model وتجربة الداشبورد

إضافة `BookingFunding` وendpoint المشتريات، ثم مركز الباقات ووضوح صف وتفاصيل
الموعد وملف العميل.

### المرحلة D — E2E والتحقق البصري

تشغيل السيناريوهات محليًا على قاعدة اختبار معزولة، ثم فحص الصفحات في المتصفح
على desktop وmobile viewport. لا يوصَف Moyasar بأنه متحقق حتى ينجح sandbox.

## 8. استراتيجية الاختبار

### اختبارات حمراء أولًا

- طلبا دفع متزامنان على آخر مبلغ مستحق: ينجح واحد فقط.
- إنشاء فاتورة بلا مستهلك اختياري: 2xx ولا تكرار عند الإعادة.
- بيع باقة يفشل دفعه: لا شراء ACTIVE ولا رصيد صالح.
- init متزامن لنفس شراء الباقة: شراء وفاتورة واحدة.
- تعديل تعريف الباقة بعد init: التفعيل يستخدم اللقطة القديمة.
- حجزان على آخر رصيد: موعد وحركة استهلاك واحدة.
- استرداد كامل مع موعد مستقبلي: رفض وقائمة المواعيد المانعة.
- إلغاء/استرداد موعد جماعي: تحرير مقعد واحد وتحديث enrollment.
- استعادة no-show وبرنامج ممتلئ: رفض بلا تجاوز سعة.
- mobile create مع `deliveryType` وmobile cancel: العقدان يعملان.
- برنامج مدفوع على الجوال: لا نجاح نهائي قبل الدفع.

### E2E للداشبورد

1. إنشاء تعريف باقة.
2. بيعها لعميل وتسجيل دفع واحد.
3. ظهور الشراء في تبويب «مشتريات العملاء» وفي ملف العميل.
4. الحجز من الرصيد وخصم وحدة واحدة.
5. ظهور «من باقة / مدفوع مسبقًا» في الصف والتفاصيل.
6. الإلغاء وإرجاع الوحدة وظهور الحركة.
7. إنشاء موعد عادي: دفع كامل، عربون ثم متبقي، ودفع في المركز.
8. تسجيل جماعي مجاني ومدفوع، إلغاء، no-show، استعادة، وحدود السعة.
9. فشل/إلغاء/إعادة webhook وعدم تكرار الدفع أو المقعد أو الرصيد.

### بوابات التحقق

- اختبارات Jest المركزة ثم backend unit/e2e/smoke الكاملة.
- dashboard Vitest وPlaywright spec المركزة ثم smoke والـ E2E الكامل المعني.
- website tests، وmobile tests + `pnpm --dir apps/mobile typecheck`.
- `pnpm openapi:sync`، ثم root typecheck/lint/build/test.
- تحقق بصري للداشبورد مع لقطات للصفحات والحالات الأساسية.
- Moyasar sandbox للإنشاء والنجاح والفشل وwebhook وإعادة المحاولة.

## 9. حدود السلامة والتسليم

- لا تعدّل أي migration موجود؛ كل قيد أو عمود جديد عبر migration إضافية.
- لا تستخدم قاعدة تطوير/إنتاج في اختبارات التنظيف؛ يثبت اسم قاعدة الاختبار قبل
  أي reset أو migrate fresh.
- تحفظ التغييرات المحلية غير المرتبطة ولا تدخل ضمن الإصلاح.
- لا commit أو push أو deploy دون إذن صريح.
- النجاح المحلي لا يسمى إثبات إنتاج، واختبارات Moyasar المموهة لا تسمى تحقق
  sandbox.

## تعريف الإنجاز

يكتمل العمل عندما تصبح كل السيناريوهات السابقة خضراء، وتظهر مصادر السداد
بصورة متسقة في القائمة والتفاصيل وملف العميل ومركز الباقات، ويثبت اختبار
التزامن عدم التحصيل أو الخصم أو حجز المقعد مرتين، مع توثيق ما تم التحقق منه
محليًا وما بقي متعلقًا ببيئة Moyasar أو النشر.
