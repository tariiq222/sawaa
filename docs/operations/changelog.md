# سجل التغييرات التلقائي

يستخدم المشروع **git-cliff 2.14.2** بالإعداد الموحد في `cliff.toml`.

## متى يُولّد؟

- بعد أي push إلى `develop` أو `main`، بما فيه الدمج عبر PR، يعمل workflow `changelog` تلقائيًا على رقم الكومِت الذي أطلق التشغيل.
- يُولّد كذلك معاينة على PRs الموجهة إلى الفرعين للتحقق من الأتمتة قبل الدمج؛ هذه المعاينة تشمل كومِت الدمج التجريبي الخاص بـGitHub.
- يحفظ التشغيل `CHANGELOG.md` الكامل و`changelog-source.txt` الذي يحدد الفرع والكومِت. من GitHub افتح **Actions → changelog → التشغيل المطلوب → Artifacts**.
- عند إنشاء إصدار كود من `main`، يستخدم workflow `release` الإعداد نفسه لتوليد تغييرات الوسم الحالي، ثم ينشرها في وصف GitHub Release ويرفق `RELEASE-NOTES.md`. تبقى قواعد تشغيل إصدار الكود الحالية، بما فيها استبعاد التغييرات الوثائقية وحدها و`[skip release]`.
- يتوفر تشغيل يدوي لـworkflow `changelog` من GitHub عند الحاجة بعد وجود ملفه على الفرع الافتراضي للمستودع. الكومِت المحلي قبل رفعه لا يطلق GitHub Actions.

مخرجات Actions محفوظة لمدة 90 يومًا أو المدة الأقل التي يسمح بها إعداد المستودع. يمكن إعادة توليد السجل من تاريخ Git لاحقًا؛ ملاحظات GitHub Release لا تتبع مدة احتفاظ Artifacts.

## ماذا يحتوي؟

يشمل تاريخ الفرع الذي شُغّل عليه، عبر تطبيقات backend وdashboard وwebsite وmobile والحزم المشتركة. تُقسم التغييرات حسب نوع الكومِت، ويظهر النطاق مثل `mobile` أو `backend` ورابط الكومِت لكل بند. عناوين الأقسام عربية، وأوصاف البنود تبقى بلغة رسائل الكومِتات الأصلية؛ لا يترجمها البرنامج ولا يستنتج معنى غير مكتوب.

تُدرج الرسائل القديمة غير المطابقة لـConventional Commits تحت «تغييرات أخرى». تُستبعد رسائل الدمج لأن الكومِتات التي أدخلها الدمج تظهر منفردة، وتُستبعد صيانة السجل من نوع `chore(changelog)`. لا تُستبعد التغييرات غير المتوافقة. تُقسم الإصدارات بحسب وسوم الكود من صيغة `vYYYY.MM.DD.N` المستخدمة أصلًا في المشروع.

## معاينة محلية

```bash
pnpm changelog
```

ينشئ الأمر `build/changelog/CHANGELOG.md` في مجلد مخرجات البناء المتجاهل في Git وفحوص الشفرة. قد تتضمن الرسائل التاريخية أسماء قديمة تمنعها قواعد الشفرة الحالية؛ وضع السجل في مجلد المخرجات يحفظ هذا التاريخ دون تغيير تلك القواعد. لا يحتاج الملف كومِتًا إضافيًا ولا يتداخل مع تغييرات المستخدم. أول تشغيل يحمّل الإصدار المحدد عبر pnpm؛ لا يتطلب تثبيتًا عالميًا. أعد التشغيل بعد تغير HEAD إذا أردت معاينة أحدث.

## عند أوامر المالك

عند «كومت» أو «ادمج» أو «انشر»، اتبع حدود الإذن وسياسة النشر المعتادة، واكتب رسائل واضحة مثل `fix(mobile): correct appointment times`. يبدأ التوليد على GitHub بعد وصول الكومِتات إلى الفرعين المحددين، فلا يلزم طلب منفصل لتوليد السجل.

هذا التوليد لا ينشئ كومِتات ولا يرفع تغييرات إلى الفروع ولا يدمجها ولا ينشر التطبيق. workflow الإصدار يحتفظ بعمله السابق في إنشاء وسوم وإصدارات الكود. السجل لا يحفظ التعديلات غير الملتزم بها، ولا يمثل دليلًا على نجاح نشر التطبيق. توثيق البيئة والمراجعة المنشورة والقبول اليدوي يبقى وفق [سياسة النشر](deployment-policy.md) و[عقد سجل النشر](deployments/README.md).

رفع هذه الإعدادات ودمجها شرط بدء التشغيل عن بُعد؛ إعدادها واختبارها محليًا لا يفعّلان GitHub Actions في المستودع وحدهما.
