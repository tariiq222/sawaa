# Sawaa single-main cutover

Use this procedure for the authorized changeover from develop to main. The deployed system follows the previously verified procedure until the new staging run is verified. Production approval and evidence are required separately under the [deployment policy](deployment-policy.md).

## Preflight

1. Inspect GitHub branch heads and open PRs. Confirm the cutover candidate includes the current main and the documented develop-only production receipt. Preserve local branches, uncommitted work, and task branches with unique commits. If either base moved, inspect and verify the new candidate before merging.
2. Confirm GitHub uses `main` as the default branch with `gh repo view --json defaultBranchRef`. Record the prior default and, if needed, change it to `main` before dispatching workflows or retiring branches. Review the candidate PR into main and verify the current required checks on its head. Configure main branch rules to require a PR, successful `gate` and `critical-real-e2e` checks, and protection against force pushes and deletion. Verify rules on GitHub, including the absence of automatic bypass for the normal merge path. Record the previous GitHub environment branch rules, then restrict the staging and production environments to main and verify the respective scoped credentials. Keep production deploy credentials in the production environment.
3. Record the active staging and production deployment IDs, runtime SHAs, and the staging project's previous Git ref and auto-deploy setting. Drain or cancel queued and running legacy publication, release metadata and TestFlight jobs. Coordinate a brief pause on new staging dispatches and develop merges.
4. Disable the legacy `release.yml` workflow in GitHub with `gh workflow disable release.yml` before the merge so a historical rerun cannot create an unverified tag. Its replacement is the reusable `production-release-metadata.yml`. Remove `PRODUCTION_RELEASE_AUTHORIZATION` from any GitHub scope visible to the old production job before the cutover merge. Verify it is absent and no old job has already received the value. The legacy script requires it before invoking OpenShip. The new manual job uses a distinct `SAWAA_PRODUCTION_ACCEPTANCE` in the production environment. Configure `SAWAA_PRODUCTION_ACTOR` there with the login approved by the owner. Populate the new acceptance record only when the owner accepts a ready staging revision for production. Keep both OpenShip Git auto-deploy settings disabled.
5. Verify the staging project and scoped hook using their existing credentials. Set only the staging project's normal Git ref to `main`. Keep the current application containers active until the new workflow deploys.

## Cutover and validation

1. Merge the checked PR into main and follow the automatic `build-images.yml` run. Verify it selects staging, skips production and release metadata, then returns a staging evidence artifact for the merge SHA.
2. Verify OpenShip staging is ready with the same SHA, all three application digests match, API, site and internal dashboard pass, and data service identities and migration metadata are preserved. Independently compare production's observed deployment ID and running SHA with the preflight record.
3. Check the negative dispatch and stale-candidate tests on the cutover PR. The first real production dispatch follows the owner acceptance and backup procedure and is observed as a separate operation.
4. Fetch and set local `origin/HEAD` to main. If no local main exists, create a tracking branch with `git branch --track main origin/main`. Run `scripts/sync-main.sh` and inspect ahead/behind without rewriting local commits. Install `scripts/install-main-sync.sh` only after verifying the desired local checkout. Run `scripts/install-main-sync.sh --uninstall-legacy` after confirming that the new launchd job works. Preserve a divergent local branch or dirty checkout for the owner.
5. Reconfirm GitHub defaults to main and current automation targets it, including Dependabot and TestFlight. Retarget or regenerate unresolved PRs and verify which old branch tips are already preserved in main. Retire develop and the merged temporary branches only when scoped cleanup is authorized and rollback readiness has been reviewed. Keep release tags and deployment receipts.

## If the new staging path fails

Stop new staging publication, wait for any triggered deployment to settle and inspect its deployment ID. Restore the prior staging ref, GitHub staging environment branch rules and OpenShip configuration. Restore the prior GitHub default branch if it changed during cutover. Then run the previous `build-images.yml` on the retained develop branch. Verify its runtime through the previously approved scoped hook. Keep the legacy production authorization and tag workflow disabled throughout. If either orchestrator lost the hook response, inspect OpenShip before any retry or ref change.
