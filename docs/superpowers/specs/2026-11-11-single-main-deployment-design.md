# فرع دائم واحد ونشر مستقل للإنتاج

الحالة: تصميم مقترح لاعتماد المالك قبل تغيير مسار النشر.

## سير العمل المطلوب

- `main` هو الفرع الدائم الوحيد على GitHub. يبدأ كل تعديل من فرع قصير مبني على `main` ويدخل إليه بطلب دمج بعد نجاح الفحوص المطلوبة. تُطبّق قاعدة طلب الدمج على GitHub ويظل الدفع المباشر محظورًا في الخطاف المحلي.
- كل دمج إلى `main` يشغّل بناء صور staging ونشرها تلقائيًا عبر المسار الحالي للصور الموثقة في OpenShip. يشمل ذلك دمج التوثيق أو تغييرات التطبيق فقط حتى يكون لكل نسخة مرشحة معرّف واضح. عند تقارب عمليات الدمج، يفوز أحدث SHA وتُسجّل النسخ المتجاوزة صراحة.
- يظل إعادة تشغيل staging يدويًا متاحًا لإصلاح تشغيل فاشل أو تطبيق إعدادات staging فقط. يحدد المدخل بيئة `staging` صراحة ويستخدم مسار الدمج نفسه.
- يختبر المالك نسخة staging. نشر الإنتاج يبدأ بتشغيل يدوي يحدد SHA المقبول، ويستخدم بناء صور الإنتاج وإعداداته الحالية. اختيار `main` عند تشغيل المهمة يحدد مصدر الـworkflow، وتحدد مطابقة SHA النسخة المرخصة للنشر.

## شروط نشر الإنتاج

1. يُشترط حدث تشغيل يدوي صريح وSHA كامل. يجب أن يساوي SHA المدخل رأس `main` عند التشغيل وأن يطابق سجل قبول المالك ومعرّف نشر staging النشط وحالة `ready` و`gitSha` من فحص صحة الباك إند. يتحقق مسار الإنتاج من صلاحية حساب GitHub الذي طلب التشغيل أو إعادته، وفق الحساب الذي يعتمده المالك. يُحفظ قبول المالك في إعداد خاص ببيئة الإنتاج تحت صلاحية الإدارة ويربط هوية المالك والوقت التالي لجاهزية staging والـSHA ومعرّف النشر. لا يُقبل القبول من مدخلات الـworkflow وحدها. دمج PR أو إعادة تشغيل مهمة staging لا يستطيع الوصول إلى وظيفة نشر الإنتاج.
2. تبقى فحوص النسخ الاحتياطي والاستعادة المعزولة، وتوافق Prisma، وتطابق بصمات الصور، وتقييد خطاف OpenShip بخدمات التطبيق. تُسلسل خطوات تعديل OpenShip ويُفحص مصدر `main` والنشر النشط على staging مجددًا قبل الخطاف. إذا سبق التشغيل دمج أحدث ولم يعد SHA المقبول رأس `main` ونسخة staging النشطة، يُرفض التشغيل ويُختبر الإصدار الجديد قبل طلب نشره. إذا تحرّك `main` بعد إرسال الخطاف، يُتحقق من النشر المثبت ويُسجل ما نُشر فعليًا ومتى تحرّك الفرع. تُربط الوسوم بنشر الإنتاج المتحقق منه فقط.
3. يستبدل SHA المثبت وسجل القبول غرض فرع `release/<date>` وطلب الدمج الثاني. تبقى الاستعادة التشغيلية للإنتاج مسارًا يدويًا منفصلًا حسب سياسة الاستعادة، وتبقى أدلة النشر مرتبطة بمعرّف النشر الفعلي.

## مواضع التغيير

| المسؤولية | موضعها |
| --- | --- |
| توجيه حدث الدمج إلى staging والتشغيل اليدوي إلى الإنتاج، وفصل الصور والإعدادات والأسرار | `.github/workflows/build-images.yml` و`staging-deploy.mjs` و`production-deploy.mjs` واختباراتهما. التحقق من المصدر وعودة مرجع OpenShip بعد تثبيت SHA يستخدمان `main` في البيئتين. |
| فحوص طلبات الدمج | `merge-gate.yml` يستهدف `main` ويحتفظ بالفحوص المطلوبة. يستمر فحص تاريخ الإصدارات المثبتة على مرشح الدمج، ويزال افتراض مزامنة `main` إلى `develop`. |
| أدوات الفريق | Dependabot يستهدف `main`. `lefthook.yml` يحظر الدفع المباشر إلى `main`. يُحوّل مزامن launchd المحلي إلى مزامنة `main` بالـfast-forward ويُزال تشغيل المزامن القديم بعد التحقق من حفظ العمل المحلي. |
| سجل التغييرات وإصدارات GitHub | `changelog.yml` يتابع `main`. يوسم إصدار GitHub بعد تحقق النشر اليدوي للإنتاج وبـSHA النشر الفعلي. تبقى وسوم وإيصالات الإصدارات السابقة. |
| TestFlight | يُحدد هدف Apple من بيئة صريحة، فينتظر الإصدار التجريبي دليل staging. بناء الملف الموجه إلى الإنتاج عملية يدوية منفصلة تستلزم دليل نشر الإنتاج لنفس SHA. |
| السياسة والإجراءات | تحديث `AGENTS.md` و`CLAUDE.md` وسياسة النشر و`sawaa-release` وإرشادات التشغيل الحالية. السجلات المؤرخة تصف ما حدث وقتها. |

## ترتيب التحويل والتحقق

1. احفظ العمل المحلي الحالي في موضعه. راجع مقارنة الفرعين وحدد SHA الأساس. في آخر فحص كان `main` سلفًا لـ`develop` والفرق الحالي في الشجرة إيصال نشر وتحديث توثيق. تُنقل هذه التغييرات إلى `main` ضمن PR التحويل بعد إعادة التحقق من الفرق. تُراجع تغييرات Authentica والاعتماديات وتعديلات الموقع في طلبات منفصلة.
2. اختبر محليًا مصفوفة الأحداث. الدفع الناتج عن الدمج يبني staging وحدها، وطلب الدمج يقتصر على الفحوص، والتشغيل اليدوي بمدخل ناقص أو SHA أو إثبات قديم يفشل قبل طلب نشر OpenShip. تُختبر أيضًا حالة دمج أحدث أثناء البناء، وفشل الاستعادة، ورفض تغيّر ملفات الترحيل، وتوجيه TestFlight والوسوم. طبّق فحوص المشروع المطلوبة على مرشح التحويل.
3. قبل الدمج التشغيلي، طبّق قاعدة طلب الدمج على `main` وأوقف تشغيلات النشر القديمة أو انتظر نهايتها. عطّل قبول الإنتاج القديم قبل تحويل المسار، وتحقق من غياب متغير القبول الذي تحتاجه النسخة القديمة من الـworkflow كي تفشل أي إعادة تشغيل قديمة قبل طلب الخطاف. يستخدم مسار الإنتاج اليدوي اسم إعداد جديدًا داخل بيئة الإنتاج، وتُجهز موافقته عند أول نشر معتمد. أوقف استقبال نشر جديد من `develop` خلال التحويل.
4. حدّث مرجع مشروع staging إلى `main` مع آلية الصور المثبتة والخطاف الحالي. ادمج مرشح التحويل عبر PR وشاهد مسار الدمج التلقائي حتى يتحقق SHA وبصمات الصور وصحة الخدمات في staging. اختبر مسار رفض نشر الإنتاج بلا قبول في بيئة اختبار. تحقق من بقاء إصدار الإنتاج السابق نشطًا بعد دمج التحويل. إذا فشل التحويل، أوقف مسار staging الجديد وأعد مرجع المشروع وتفعيل نشر staging إلى `develop` عبر مساره السابق مع استمرار تعطيل قبول الإنتاج القديم.
5. بعد نجاح staging ومراجعة إعدادات GitHub وOpenShip والمزامنة المحلية، أعد التحقق من حفظ الفروع القديمة ومن حالة PRs المفتوحة، ثم يمكن إيقاف `develop` وحذف الفروع المؤقتة المدموجة في خطوة تنظيف مصرح بها.

يُقبل التحويل عند مشاهدة دمج ناجح إلى `main` ينتهي إلى staging بنفس SHA، مع تحقق عملي من أن النشر إلى الإنتاج لا يبدأ على حدث الدمج. يُثبت أول نشر إنتاج حقيقي لاحقًا عند طلب المالك اليدوي لنسخة قبلها على staging.
