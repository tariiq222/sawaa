# دليل إطلاق المحادثة الموحدة على الويب

هذا الدليل خاص بإطلاق محادثة الذكاء الاصطناعي الإدارية في الموقع، وسجل العميل،
وصندوق الاستقبال في لوحة التحكم. لا يجيز هذا الدليل نشر إعدادات، أو تغيير رايات
الإنتاج، أو حذف واتساب أو بياناته؛ تلك أعمال تشغيلية تتطلب موافقة مستقلة.

> نطاق المساعد: التعريف بالخدمات والمعالجين والتوافر، وإدارة مواعيد العميل
> نفسه بعد تسجيل الدخول. لا يقدّم تقييماً صحياً أو إرشاداً سريرياً أو تعاملاً مع
> الطوارئ.

## حالة الإصدار وبوابة المنع

ابدأ من نسخة تحتوي تكامل المحادثات واختباراتها، ثم سجّل في تذكرة الإطلاق:

- رقم الإصدار أو `git commit` وصورة الخدمات (digest أو tag).
- مالك الإطلاق، منفذ التحقق، وقت البدء UTC، والبيئة المستهدفة.
- نتيجة اختبارات التكامل المحلية وقيودها. الاختبارات المحلية لا تثبت اتصال
  Postgres أو Redis أو Playwright الحقيقيين ما لم تُنفذ على بيئة اختبار مخصصة.

### شرط build لتشغيل واجهة الموقع

`NEXT_PUBLIC_WEB_CHAT_ENABLED` متغير عام يقرأه `apps/website/app/layout.tsx`،
ولذلك يجب أن تصل قيمته إلى عملية `next build` نفسها؛ تغيير متغير بيئة الحاوية
بعد بناء الصورة لا يغيّر JavaScript المنشور.

`apps/website/Dockerfile` يعرّف المتغير كـ build argument افتراضه `false` ثم
يمرره إلى بيئة البناء، و`docker/docker-compose.prod.yml` يمرره ضمن
`website.build.args` بالقيمة المغلقة نفسها عند غيابه. يجب أن يمرر Dokploy أو أي
مسار نشر بديل القيمة كـ build argument مكافئ، لا كـ `website.environment` وقت
التشغيل فقط.

تحقق من artefact مغلق أولاً ثم من artefact مفعّل؛ لا تعتمد على اسم المتغير في
لوحة النشر وحده.

## الإعدادات المطلوبة والتحقق الآمن

لا تضع قيمة سر أو token أو URL داخلي في التذكرة أو لقطات الشاشة. يتحقق منفذ
الإطلاق من **وجود** الأسرار في مدير الأسرار فقط، دون عرض قيمها.

| المجال           | تحقق قبل النشر                                                                                                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| الخلفية          | `WEB_CHAT_ENABLED=false` في الإصدار المغلق، ثم `true` فقط في المرحلة المصرح بها.                                                                                  |
| جلسة الضيف       | `CHAT_GUEST_TOKEN_SECRET` موجود وقوي وفريد؛ لا يطبع أو ينسخ إلى السجل.                                                                                            |
| الحدود           | القيم الإيجابية المعتمدة لـ `CHAT_MAX_MESSAGE_LENGTH` و`CHAT_RATE_LIMIT_PER_MINUTE` و`CHAT_DAILY_TOKEN_BUDGET` و`CHAT_GUEST_SESSION_DAYS` و`RETENTION_CHAT_DAYS`. |
| الذكاء الاصطناعي | وجود اعتماد مزود المحادثة، وصلاحية `OPENROUTER_BASE_URL` و`OPENROUTER_CHAT_MODEL` دون كشف `OPENROUTER_API_KEY`.                                                   |
| البنية           | backend وPostgres وRedis والـworker سليمة، وCORS يضم origin الموقع الفعلي بلا trailing slash.                                                                     |
| الموقع           | `NEXT_PUBLIC_API_URL` صحيح وقت البناء، و`NEXT_PUBLIC_WEB_CHAT_ENABLED` يمرر وقت **البناء** بعد معالجة المانع أعلاه.                                               |
| العزل            | بيئة الاختبار تحتوي حساب عميل وحساب استقبال ومحادثة/حجزاً قابلين للحذف، ولا تستخدم بيانات مستفيد حقيقية.                                                          |

يمكن توثيق الحضور بصيغة `present / valid / not-applicable` فقط. يجب أن تكون
الاستعلامات التشخيصية read-only، وأن تعود الصحة جاهزة قبل الانتقال. إذا كان
OpenRouter غير مهيأ، يتوقع مسار المساعد فشلاً متحكماً به؛ لا يفتح للمستخدمين
حتى يثبت اختبار المزود نجاحه في البيئة المعتمدة.

## مراحل الإطلاق

### 1. نشر مغلق (إلزامي)

انشر الخلفية مع `WEB_CHAT_ENABLED=false`، وابنِ الموقع مع
`NEXT_PUBLIC_WEB_CHAT_ENABLED=false`. أبقِ إعدادات واتساب وكوده كما هي في هذه
المرحلة.

تحقق يدوياً من الآتي:

1. صفحة الموقع لا تعرض أيقونة الذكاء الاصطناعي، ولا زر واتساب بديل.
2. طلبات `/api/v1/public/chat/**` و`/api/v1/public/me/chat/**` تعود 404 عند
   تعطيل الخلفية؛ لا تختبرها على بيانات حقيقية.
3. مسارات الصحة وCSRF غير المتصلة بالمحادثة ما زالت تعمل.
4. لوحة الاستقبال `/conversations` لا تفتح محادثات قائمة بلا صلاحية صحيحة.

سجل وقت النشر وحالة كل نقطة قبل المتابعة.

### 2. تمكين داخلي محدود

بعد إزالة مانع build أعلاه، أنشئ صورة موقع مفعلة (`NEXT_PUBLIC_WEB_CHAT_ENABLED=true`)
وافتح الخلفية (`WEB_CHAT_ENABLED=true`) في بيئة داخلية أو نطاق محمي يسمح فقط
لفريق الإطلاق. لا تفعّل أحد الجانبين منفرداً: واجهة مفعلة مع API مغلق تؤدي إلى
فشل 404، وAPI مفتوح مع واجهة مخفية ليس اختبار قبول للموقع.

نفذ مسار القبول التالي بحسابات اختبار منفصلة. دوّن `PASS/FAIL` ووقت UTC لكل
خطوة، ولا تنسخ نص المحادثة أو أرقام الهواتف أو معرفات الحجوزات الحقيقية.

| الخطوة | الإجراء                                                                 | النتيجة المطلوبة                                                             |
| ------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 1      | زائر يفتح أيقونة الذكاء ويطرح سؤالاً إدارياً عن خدمة أو معالج أو توافر. | تنشأ محادثة واحدة ويأتي رد إداري فقط، بلا تقييم صحي.                         |
| 2      | الزائر يطلب حجزاً أو التحكم بموعده.                                     | تظهر الحاجة لتسجيل الدخول، ويحفظ الاستئناف بأمان.                            |
| 3      | سجّل الدخول كعميل الاختبار.                                             | تستأنف المحادثة وتُعرض مواعيد العميل نفسه فقط.                               |
| 4      | اطلب حجزاً مع وجود موعد قائم.                                           | يظهر الموعد القائم قبل أي إنشاء جديد، ويتطلب إقراراً صريحاً ثم تأكيد الحجز.  |
| 5      | أكّد العملية مرة واحدة ثم أعد المحاولة/انقر مرتين.                      | حجز واحد فقط أو نتيجة idempotent واضحة؛ لا ينشأ تكرار.                       |
| 6      | افتح لوحة حساب العميل.                                                  | يظهر سجل المحادثة ونتيجة العملية لنفس العميل فقط.                            |
| 7      | اطلب تحويل المحادثة للاستقبال.                                          | تصبح في انتظار الاستقبال وتظهر في `/conversations`.                          |
| 8      | موظف استقبال الاختبار يستلمها ويرد.                                     | يصبح مالكاً لها، ويصل رده في نفس السجل، ولا يُنشئ المساعد رداً بعد الاستلام. |
| 9      | الموظف يعيدها للمساعد ثم يغلقها.                                        | تعود للمساعد عند الإعادة، ثم تظهر مغلقة بعد الإغلاق.                         |

### 3. اختبارات الفشل قبل الجمهور

نفذ هذه الحالات على بيانات قابلة للحذف فقط:

- مزود الذكاء غير متاح: تحفظ رسالة المستخدم ولا يتكرر الطلب أو الحجز؛ تظهر
  حالة فشل قابلة لإعادة المحاولة وتصلح المحادثة للتحويل للاستقبال.
- عملية منتهية الصلاحية: لا يُنشأ أو يُعدّل حجز عند التأكيد المتأخر.
- تغير slot بين العرض والتأكيد: تفشل العملية بشكل مفهوم ولا تحجز slot آخر.
- استلام متزامن من موظفين: واحد فقط يستلم؛ الثاني يرى تعارضاً ولا يستطيع الرد.
- ملكية خاطئة: عميل ثانٍ أو ضيف ثانٍ لا يقرأ أو يعدل محادثة غيره.
- CSRF/CORS غير صالحين: الطلب المغير للحالة يرفض، والـorigin المعتمد فقط يحصل
  على مسار bootstrap الصحيح.
- عدم تطابق الرايات: أوقف إحدى الرايتين في بيئة الاختبار للتأكد من أن الأثر
  مفهوم، ثم أعدهما للحالة المصرح بها قبل مغادرة البيئة.

أي فشل في العزل أو تكرار الحجز أو استمرار رد الذكاء بعد استلام الموظف هو
حاجز P0: أغلق الرايتين، احفظ أدلة خالية من البيانات الشخصية، وافتح حادثة.

### 4. فتح الجمهور وفترة الاستقرار

بعد قبول داخلي موثق وموافقة مالك الإطلاق، ابنِ وانشر artefact الموقع المفعّل
وافتح الخلفية. تحقق من الموقع العام بأداة متصفح جديدة أن أيقونة الذكاء ظاهرة
وأن زر واتساب غير ظاهر. لا تحذف أي تكامل واتساب في هذه المرحلة.

حدد قبل الإطلاق مدة استقرار ومالك مراقبة وحداً رقمياً للإيقاف لكل مؤشر:

- نسبة أخطاء HTTP للمحادثة وعمليات الحجز.
- زمن انتظار رد المساعد، وفشل/إعادة محاولة المهام الخلفية.
- استخدام/تكلفة الذكاء بالنسبة للحد اليومي.
- نسبة التحويل إلى الاستقبال، ووقت أول استلام أو رد من الاستقبال.
- نسبة نجاح العملية، حالات انتهاء الصلاحية أو تغير slot.
- محاولات الحجز المكررة والحجوزات المنشأة فعلياً.
- محاولات ownership/CSRF/CORS المرفوضة.

لا تسجل body الرسالة أو الاسم أو الهاتف أو cookie أو token أو مفاتيح المزود
ضمن مراقبة الإطلاق. استخدم معرف حالة اختبار أو تجزئة غير قابلة للعكس إن لزم
ربط الأحداث.

## سجل الأدلة

احتفظ بهذا الجدول في تذكرة مقيدة الوصول، لا في المحادثة أو logs العامة:

| الحقل          | مثال آمن                                            |
| -------------- | --------------------------------------------------- |
| وقت UTC        | `2026-08-14T12:00:00Z`                              |
| البيئة والنسخة | `staging` + image digest مختصر                      |
| حالة الرايات   | `backend=true, website-build=true`                  |
| حالة الاختبار  | `guest-to-client-booking: PASS`                     |
| استجابة HTTP   | `operation-confirm: 200`                            |
| أثر البيانات   | `one disposable booking created`                    |
| الاستلام       | `staff-claim: PASS; no assistant reply after claim` |
| المراقبة       | `window complete; thresholds not exceeded`          |
| القرار والمالك | `approved for next stage`                           |

استبدل كل معرف محادثة/حجز حقيقي باسم حالة اختبار أو digest أحادي الاتجاه.

## الرجوع للخلف

### قبل إزالة واتساب (حتى نهاية Task 13)

1. أوقف استقبال محادثات ويب جديدة بإعادة الخلفية إلى
   `WEB_CHAT_ENABLED=false`.
2. ابنِ وانشر صورة موقع جديدة مع `NEXT_PUBLIC_WEB_CHAT_ENABLED=false`؛ لا
   تعتمد على runtime environment فقط.
3. تحقق من اختفاء الأيقونة ومن 404 لمسارات المحادثة، ثم راقب المهام المؤجلة
   حتى تستقر.
4. أبقِ واتساب كما هو. هذه المرحلة لا تحذف كوداً أو secrets أو جداول.

### بعد إزالة واتساب (Task 14) وقبل الهجرة التدميرية

الإجراء الأول يبقى إغلاق رايتي محادثة الويب. استعادة واتساب، إن تقررت، تكون
فقط بنشر صورة سابقة متوافقة ضمن نافذة الرجوع المعتمدة ومع إعدادات المزود التي
حُفظت خارج الكود. لا تعِد تفعيل webhook أو worker أو secrets من الذاكرة أو من
سجلات التطبيق.

### بعد Task 15

بعد هجرة حذف الجداول، الرجوع يتطلب صورة سابقة **وقاعدة بيانات من النسخة
الاحتياطية المتوافقة** وفق [دليل الاستعادة](restore-runbook.md). لا تطبق صورة
قديمة وحدها على schema أحدث.

## بوابات إتمام Tasks 14 و15

### Task 14: إزالة كود وواجهات واتساب

لا تبدأ إلا بعد توفر جميع الآتي:

- اكتمال النشر المغلق، والقبول الداخلي، وفتح الجمهور وفترة الاستقرار في هذا
  الدليل مع أدلة خالية من PII.
- عدم وجود حادثة مفتوحة تخص العزل أو التكرار أو handoff، وموافقة صريحة من مالك
  الخدمة على القطع.
- توثيق خطة rollback ونافذتها، وحفظ إعدادات واتساب اللازمة للرجوع خارج الكود.
- تحقق تشغيلي أن webhook/worker لا يستقبلان أو يرسلان قبل إزالتهما.

Task 14 يزيل runtime والواجهات فقط؛ تبقى الجداول والبيانات إلى Task 15.

### Task 15: الهجرة التدميرية للبيانات

هذه البوابة تتطلب موافقة تشغيلية صريحة منفصلة. قبل أي migration:

1. خذ نسخة قاعدة بيانات مشفرة وسجّل timestamp وchecksum ومسار الاستعادة، ثم
   أثبت اختبار الاستعادة المتفق عليه.
2. نفذ counts read-only لجداول `WhatsappAgentConfig` و`WhatsappConversation`
   و`WhatsappMessage` و`ChatSession` و`ChatMessage`، وكذلك لسجلات
   `Booking` و`Client` ذات المصدر `WHATSAPP`.
3. أي count غير صفري يوقف الحذف: يحدد المالك mapping/احتفاظاً مناسباً أولاً.
4. شغّل migration الإضافية الجديدة في staging، ثم smoke للحجز واللوحة، ثم
   انتقل للإنتاج بموافقة منفصلة.

لا تعدل migration تاريخية، ولا تحذف قيمة enum تاريخية ما دامت سجلاتها موجودة.
