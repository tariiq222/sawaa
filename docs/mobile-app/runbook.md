# خطوات إعداد إصدار الجوال وTestFlight

آخر مراجعة عملية: 2026-09-28، البناء `1.0.0 (13)`. هذا الملف هو تسلسل التشغيل الخاص بتطبيق `apps/mobile`؛ سجّل نتيجة **كل** تغيير أو تحديث للجوال في ملف مؤرخ تحت `releases/`، وحدّث هذه الخطوات عندما تتغير الأدوات أو المراحل. لا تنسب حالة بناء قديم إلى مصدر تغيّر بعده. الحالة المرصودة الأحدث في [سجل 2026-09-28](releases/2026-09-28.md).

## تثبيت نطاق العمل

1. افحص `git status --short` والفرع وفرق التعديلات، واحفظ أعمال الآخرين. اقرأ تعليمات التطبيق وسياسة النشر قبل العمليات التي تتطلبها.
2. دوّن commit/التغييرات المحلية ورقم الإصدار والبيئة والبناء المرشح. لا تعتمد أرقامًا قديمة من هذا السجل كحالة حالية.
3. شغّل أوامر الجوال باستخدام `pnpm --dir apps/mobile`؛ أوامر workspace الأساسية لا تغطيه.

## الفحوص والبناء

1. نفّذ typecheck واختبارات التغيير المناسبة. عند إصدار تغييرات واسعة، شغّل مجموعة الجوال وسجل suites/tests ونتائج lint وحدود التحقق.
2. تحقق من EAS account/project والـbundle/team/ASC ID، ومن متغير API الإنتاج وملف Firebase السري دون طباعة محتواه.
3. تحقق من archive نظيف يستبعد `.env` و`private-config` وملفات iOS القديمة، ومن نجاح تثبيت frozen واعتماد shared. لا تنسخ المفاتيح أو الشهادات إلى الوثائق.
4. من `apps/mobile` اطلب بناء iOS بـproduction عبر EAS بعد تفويضه؛ سجل build ID وحالته النهائية. `eas.json` يستخدم `appVersionSource: remote` و`autoIncrement: true`؛ تحقق من رقم البناء الفعلي، ولا تخمّنه. يمكن لـEAS ضم تعديلات working tree دون commit عندما لا يكون `requireCommit` مفعلًا. نفّذ `eas build:inspect --platform ios --profile production --stage archive --output <private-temp-dir>` وتحقق من وجود الملفات المعدلة وغير المتتبعة المقصودة. لا تكتف بوجود `gitCommitHash` في بيانات EAS لإثبات محتوى الأرشيف.
5. نزّل `.app` عبر `eas build:download --build-id <EAS-build-id>`، ونزّل IPA من `artifacts.buildUrl` لنفس البناء في مساحة مؤقتة خاصة؛ تحقق من هوية كليهما ولا تحفظ رابط التنزيل المؤقت في Git. افحص `.app` باستخدام `codesign --verify --deep --strict`، ثم Info.plist والـentitlements: bundle/version/build/team و`get-task-allow=false` وبيئة push.
6. افحص الحزمة للتأكد من API الإنتاج وغياب fixture/عناوين localhost وتطابق أصول IBM المطلوبة. سجّل JSON منقحًا فقط؛ لا تحفظ روابط signed download أو بيانات الحساب أو مفاتيحه.
7. إذا تغيّر المصدر بعد البناء، أنشئ مرشحًا جديدًا؛ لا تجمع أدلة بناء قديم مع كود جديد.

## الصور

1. التقط من iPhone/iPad بأبعاد المتجر المطلوبة مع بيانات اصطناعية؛ لا تستخدم بيانات عملاء أو debug banners.
2. راجع بصريًا IBM والعربية والمحاذاة والتبويبات والقوائم وأزرار الرجوع، واختبر AR→EN→AR وبدءًا باردًا ودافئًا.
3. اعرض الصور على المالك قبل استخدامها. انسخ الصور المعتمدة دون إعادة ضغط أو تعديل، وأنشئ SHA256SUMS ثم تحقق منه.
4. ارفع خمس صور لكل جهاز بالترتيب المعتمد: home، specialists، profile، booking، login. تحقق من الحفظ بعد إعادة الفتح، لا من انتهاء اختيار الملفات فقط.

## تسليم Apple

1. أكمل الحساب التجريبي واختبره على المرشح النهائي، ثم حقول جهة الاتصال والخصوصية والعمر والتصنيف والحقوق والسعر والدول والتشفير وفق قرارات المالك.
2. تحقق من تفويض API Access/إنشاء المفاتيح والاتفاقات القانونية كلما تطلبت صلاحيات جديدة. لا تستخدم موافقة شهادة التوقيع بديلًا عنها.
3. مفتاح App Store Connect المحلي السابق محفوظ في المسار المتجاهل `apps/mobile/private-config/app-store-connect/` بصلاحيات مقيدة. اقرأ `metadata.json` محليًا للحصول على `keyId` و`issuerId`، وحدد المجلد نفسه في `API_PRIVATE_KEYS_DIR`. لا تنشئ مفتاحًا آخر قبل التحقق من هذا المفتاح، ولا تنسخ ملف `.p8` أو قيمته إلى EAS أو Git أو السجل. إذا كان `eas build --auto-submit` يطلب مفتاحًا جديدًا، أوقف خطوة الإرسال التلقائي وأكمل البناء ثم ارفع IPA باستخدام `xcrun altool --upload-app -f <verified.ipa> --type ios --apiKey <keyId> --apiIssuer <issuerId> --output-format json`. لا تحفظ رابط تنزيل EAS المؤقت في ملفات متتبعة.
4. تحقق من IPA قبل الرفع: سلامة ZIP و`CFBundleIdentifier=sa.sawa.app` ونسخة التطبيق ورقم البناء. سجّل EAS build ID وApple delivery UUID، وانتظر ظهور `Build Uploads: Complete` ثم حالة البناء في App Store Connect. نجاح `altool` وحده لا يثبت اكتمال معالجة Apple. عند استعلام Apple API بتوكن ES256 موقّع في Node.js، استخدم `dsaEncoding: 'ieee-p1363'` (توقيع JWS ذي 64 بايت؛ توقيع DER الافتراضي يعيد 401). لا تحفظ التوكن أو المفتاح في التقارير. توكن الاستعلام بمفتاح Developer قد ينجح للقراءة والرفع لكن يفشل بـ403 عند تعديل إقرار التشفير؛ لا تعتبره عطلًا في المعالجة.
5. عالج `Missing Compliance` لكل بناء حسب الاستخدام الفعلي للتشفير. للبناء 9 استُخدمت إجابة المالك السابقة `None of the algorithms mentioned above`؛ راجعها مجددًا إذا تغيرت مكتبات التشفير أو سلوكها. أضف نص `What to Test` واحفظه، ثم أضف البناء إلى `Sawaa Internal` وتحقق بعد إعادة فتح الصفحة من ظهور المجموعة وعدد المختبرين. لا تعتبر الرفع أو الإضافة تثبيتًا على الجهاز.
6. اختبر على جهاز فعلي: الدخول والجلسة، المواعيد، الحجز، الدفع والعودة وفق sandbox المصرح به، push وتفاعله، وإغلاق الحساب. سجل ما لم يُختبر صراحة.
7. أرسل المراجعة/انشر فقط ضمن تفويض المالك وبعد اكتمال المتطلبات؛ حدّث سجل الإصدار بحالة Apple الحقيقية وتاريخها. نشر backend للإنتاج له تفويض مستقل.

احتفظ بتمييز واضح بين: كود محلي، فحوص، محاكي، أرشيف موقّع، معالجة Apple، تثبيت TestFlight، قبول المراجعة، وإتاحة عامة. نجاح واحدة لا يثبت التالية.

## تحقق تدفق الحجز الحالي (مراجعة مصدر 2026-09-30)

- المعالج الجديد: `booking/[serviceId]` يجمع المدة ونوع الزيارة والوقت، ثم `booking/confirm` يجمع المراجعة وطرق الدفع. `public-booking/confirm` يعرض التأكيد للزائر، ثم يعيده OTP أو حساب المراجعة إلى تأكيد العميل مع السعر المختار. `booking/schedule` يبقى للتوافق مع الروابط السابقة.
- `booking/payment` يحتفظ باستئناف حجز/فاتورة قائمة؛ لا توجّه إليه مسودة جديدة بعد المصادقة. اختبر بقاء الدفع في المركز بعد دخول الزائر، مع عدم تحويل فاتورة قائمة إلى دفع في المركز.
- افصل حالات عدم توفر المواعيد عن فشل API، وتحميل طرق الدفع عن فشلها وعن عدم وجود طرق مفعلة. اختبر إعادة المحاولة في كل خطأ.
- قبل أي إصدار: أنشئ حجزًا ثم افشل بدء الدفع/فتح المتصفح وأعد المحاولة وتحقق من عدم إنشاء حجز ثان، وكرر بعد إعادة فتح الشاشة. نجاح اختبارات mocks لا يثبت تكامل المزود أو 3DS أو جهازًا فعليًا.
