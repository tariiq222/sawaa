# Sawaa Safe Improvement Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. If delegation is explicitly selected under AGENTS.md, use superpowers:subagent-driven-development with the ownership below. Steps use checkbox (`- [ ]`) syntax for tracking. This document is a proposal, not execution or deployment authorization.

**Goal:** معالجة مخاطر المال والحجوزات والبيانات ثم تحسين الصيانة والأداء، مع الحفاظ على واجهة الموظفين وبيانات العملاء.

**Architecture:** نبقي modular monolith والـvertical slices. نوحد الحسابات والحالات ونوسع outbox الموجود، ثم نعالج عقود القراءة والحدود المعمارية تدريجيًا. الإصلاح التاريخي منفصل عن منع الأخطاء الجديدة.

**Tech Stack:** pnpm/Turborepo، NestJS 11، Prisma 7، PostgreSQL، Redis/BullMQ، Next.js 15، React 19، TanStack Query، Jest/Vitest/Playwright.

**Spec:** [التصميم والقيود الملزمة](/Users/tariq/code/sawaa/docs/superpowers/specs/2026-09-05-safe-improvement-design.md).

## Global Constraints

- المشروع single-tenant لمركز واحد؛ لا organization switching ولا subscription billing.
- تبقى Next.js 15 وReact 19 وNestJS 11 وPrisma 7؛ لا ترقية framework أو إعادة تسمية packages ضمن هذه الخطة.
- المبالغ داخل النظام أعداد صحيحة بالهللة؛ تبقى وحدات التخزين الحالية، وVAT الافتراضي 0 مع حفظ قيم الفواتير التاريخية.
- تبقى الصفحات والمسارات والقائمة الجانبية وترتيب النماذج والأزرار الأساسية وأسماء الأعمال مألوفة؛ العربية وRTL والترجمة الحالية إلزامية.
- المصادقة والصلاحيات وCASL ودلالات التوكن لا تتغير ضمن إعادة التنظيم؛ أي تغيير فيها يحتاج نطاقًا واعتمادًا صريحين.
- تنفيذ تعديل مالي يحتاج اعتماد المالك، وdashboard smoke وMoyasar sandbox قبل نشر المسار المتأثر.
- لا تغيير لمفاتيح التشفير أو AAD أو أسرار مزودي الخدمة أو إعداداتهم الإنتاجية ضمن هذه الخطة.
- المهاجرات إضافية فقط؛ لا تعديل migration تاريخية، ولا حذف أو استبدال بيانات العملاء لإكمال مهاجرة.
- لا تعديل لسعر فاتورة أو إيصال صادر أو snapshot تاريخية كوسيلة لإخفاء اختلاف محاسبي.
- كل تغيير endpoint/DTO يصاحبه pnpm openapi:sync، ومراجعة packages/api-client اليدوي إذا كان مستهلكًا للعقد.
- build وdashboard typecheck يعملان بالتتابع، وليس بالتوازي، لمنع سباق .next/types.
- اختبارات البيانات تستخدم REAL_E2E_DATABASE_URL لقاعدة معزولة مثبتة الهوية؛ لا reset أو seed على الإنتاج.
- لا بيانات عملاء أو أسرار أو نسخ قواعد بيانات في Git أو مخرجات CI أو سجلات عامة.
- لا commit أو push أو merge أو deploy أو تعديل سجلات فعلية دون تفويض المستخدم المناسب؛ طلب الخطة لا يمنح هذا التفويض.

## 3. B0 — تثبيت خط الأساس قبل أي تعديل سلوكي

**الملفات المقترحة الجديدة:** `docs/operations/safe-improvement-baseline.md` و`docs/operations/safe-improvement-release-log.md`. تحتوي نتائج وأعدادًا وروابط أدلة محمية، دون سجلات عملاء أو أسرار.

**العقد الناتج:** SHA منشور مثبت، وSHA المرشح، وقائمة migrations، ومصفوفة رحلات، وقيم مرجعية للمال والبيانات والأداء، وقرار مالي موثق. كل حزمة تقرأ هذا العقد.

- [ ] قراءة تعليمات الجذر وCLAUDE.md للنطاق المتأثر وpackages/api-client قبل التنفيذ. مقارنة هذه الخطة مع أعمال 2026-08-31؛ المهمة الموجودة والمنفذة تحتاج إثباتًا حاليًا لا إعادة كتابة تلقائية.
- [ ] تشغيل `git status --short --branch` و`git log -8 --oneline` و`git worktree list` و`git rev-parse HEAD`. الحالة عند كتابة الخطة: `main` نظيف ومتقدم 7 عن مرجع `origin/main` المحلي، وHEAD=`703e9444`. لا نفترض أنها النسخة المنشورة، ولا نشحن السبعة جميعًا تلقائيًا.
- [ ] قراءة SHA/image digest الفعلي من منصة النشر، بعد توفر الوصول، ومقارنته بالمصدر. تحديث remote refs عند التنفيذ المصرح به. إنشاء worktree معزول من قاعدة التكامل المتحققة؛ النقل إلى develop ثم main حسب مسار المستودع المعتمد. لا إصلاحات مباشرة على main ولا force-push.
- [ ] اعتماد سياسة التحصيل بعد الاسترداد وقاموس التقرير الزمني. إذا لم يُعتمد تغيير التاريخ، يبقى createdAt أثناء إصلاح حساب التقرير؛ يظل تغيير semantics مؤجلًا كقرار منفصل، ولا يحجب تصحيح الحساب المثبت.
- [ ] إثبات أن قاعدة الاختبار معزولة: عرض host/database بعد تنقيح الأسرار، التحقق من allowlist البيئة ومن current_database()؛ إعداد outbound إلى SMS/Email/Zoom/Moyasar sandbox أو fake adapters. لا تشغيل migrations/seed قبل هذا الإثبات.
- [ ] توثيق backup مشفر حديث للإنتاج وخطة الاحتفاظ به، وتجربة restore إلى قاعدة منفصلة مع منع الإرسال الخارجي. قياس مدة الاستعادة والتحقق من أعداد الكيانات وعينات العلاقات والمبالغ، دون استبدال الإنتاج. يتطلب نسخ بيانات العملاء تفويض الوصول المناسب.
- [ ] جرد read-only للأعداد والمجاميع والحالات والفواتير والدفعات والاستردادات والأرصدة وoutbox وintake المكرر ومراجع الأشخاص المفقودة. البيانات التفصيلية تحفظ خارج Git.
- [ ] تثبيت fixtures صناعية وتصوير الرحلات الحالية: موظف استقبال يحجز ويحصّل، موظف يرى مواعيده، إدارة تسترد وتقرأ تقريرًا، عربون ثم باقي، برنامج ينتظر الاكتمال، رصيد باقة وحجز منه. لا تغيير للصلاحيات أو طرق الدفع المفعلة لتمرير الفحوص.
- [ ] تسجيل الأخطاء المرجعية والأداء وqueue lag وRSS وpool usage في بيئة مشابهة للإنتاج. أي أرقام خدمة مستهدفة لاحقًا تكون أهدافًا مقترحة حتى تقارن بهذا القياس.

**قبول B0:** يمكن للمراجع تحديد ما هو محلي وما هو منشور، وإعادة التشغيل على قاعدة آمنة، واسترجاع نسخة في بيئة منفصلة، وتحديد الفرق المرئي المسموح. نقص الوصول للإنتاج يُسجل كحاجز نشر، ولا يمنع إكمال إصلاحات محلية معزولة أو الخطة.

## 5. اختبار القبول من طرف إلى طرف

تنفذ الحالات الآتية على بيانات اختبار معزولة. يلزم إثبات UI → API → DB → event/consumer حيث ينطبق، لا مجرد وجود اسم test.

| الرحلة | النتيجة اللازمة |
|---|---|
| تحصيل فاتورة 500 ريال بعد تحصيل 500 واسترداد 200 | منع تحصيل 500 إضافية؛ تطبيق سياسة إعادة التحصيل المعتمدة دون تجاوز صافي 500 |
| طلبان مختلفا المفتاح يدفعان الرصيد الأخير بالتزامن | لا يتجاوز الإجمالي المستحق؛ الخاسر conflict واضح |
| إعادة نفس طلب التحصيل بعد timeout | نفس Payment/Invoice، ولا تحصيل جديد |
| Redis متوقف بعد commit التحصيل | المال محفوظ وoutbox PENDING؛ عند التعافي ينتقل الحجز مرة واحدة |
| crash بعد نشر الحدث وقبل وضع PUBLISHED | إعادة تسليم آمنة دون تكرار أثر الحالة/الرصيد |
| فشل في منتصف إلغاء برنامج متعدد المواعيد | rollback لجميع التغييرات، ولا حدث إلغاء مرئي |
| DEPOSIT_PAID مع فاتورة PAID وحذف عميل/موظف | رفض الحذف وحفظ الارتباط، ولو تأخر مستهلك الدفع |
| تحصيل/حجز جديد يتسابق مع حذف الشخص | تسلسل واحد صحيح؛ لا حجز نشط لشخص محذوف |
| طلبا intake متزامنان مع بيانات مختلفة | استجابة حالية واحدة وإجابات سابقة محفوظة حسب عقد النسخ، دون lost update صامت |
| 201+ حجز موزعة على الأنواع والفترات | الرسم يشمل الجميع، والنوع الفردي ظاهر، وإجمالي الأنواع يساوي الإجمالي |
| اعتماد دفعة/استرداد مع فاتورة مخزنة في cache | تحديث الفاتورة والحجز المتأثرين في نفس الجلسة |
| Reset مع بحث وتاريخ وطريقة وحالة | إزالة كل الفلاتر وإعادة الصفحة الأولى |
| تقرير فرع أ وموظف محدد | لا استرداد أو خصم من نطاق آخر؛ 100−10=90 |
| حجز بالرصيد وآخر رصيد بالتزامن ثم إلغاء | فائز واحد، استهلاك مرة، إعادة مرة، ولا فاتورة جديدة |
| حساب بلا permission يحاول المسار الجديد/القديم | نفس الرفض السابق، ومنع تسريب بيانات أو host meeting URL |
| backend جديد مع dashboard قديم ثم جديد | العقود القديمة تعمل خلال نافذة النشر |

الرحلة البنكية تختبر فقط إن كانت مفعلة في البيئة المستهدفة؛ لا تفعيل طريقة دفع معطلة ضمن التحسين. website/mobile يتحققان كعملاء للعقود المشتركة، ولا يتوسع النطاق إلى إعادة تصميمهما.

## 6. بوابات التحقق

لكل تغيير سلوكي: اختبار مستهدف يفشل على السلوك السابق لسبب العيب، ثم ينجح بعده؛ تُحفظ نتيجة الأمر وSHA. اختبارات real-DB لا يسمح بتجاوزها في البوابة المالية. انخفاض عدد الاختبارات أو زيادة skip يحتاج تفسيرًا.

بعد تكامل المرحلة يشغل المسؤول مرة واحدة، وفق سطح التغيير:

```bash
pnpm --filter=backend run test
pnpm --filter=backend run test:e2e:real
pnpm --filter=dashboard test
pnpm --filter=backend run typecheck
pnpm --filter=dashboard run typecheck
pnpm --filter=backend run lint
pnpm --filter=dashboard run lint
pnpm check:api-client-drift
pnpm check:dashboard-api-drift
pnpm check:openapi-coverage
pnpm check:legacy-multitenant
pnpm --filter=dashboard run e2e:smoke
```

هذه أوامر تنفيذ مستقبلية تحتاج خدمات وبيئة الاختبار الصحيحة. `pnpm openapi:sync` يأتي قبل اختبارات العقود عند تغيير endpoint، ثم تتم مراجعة diff. `pnpm build` و`pnpm typecheck` في بوابة الإصدار بالتتابع؛ لا داعي لتكرار كل شيء لكل تعديل صغير. عند تأثر shared/api-client، تُشغل typechecks المستهلكين ومنها `pnpm --dir apps/mobile typecheck`؛ mobile خارج root workspace.

المهاجرات تُفحص بسكربت `scripts/check-prisma-migration-immutability.mjs` بعد قراءة واجهته واستخدام قاعدة المقارنة الحقيقية للـPR؛ لا مقارنة بمرجع محلي قديم وكأنها CI حديثة.

**المرجع التاريخي للمراجعة فقط:** 7,128 backend unit ناجحًا، و1,967 dashboard، و25 standard E2E؛ 139 real-DB متجاوزًا. لا نعد هذه أرقام تنفيذ الخطة ولا نشرًا ناجحًا. التخطيط الحالي لم يعد تشغيل هذه الحزم.

## 7. دفعات النشر والتراجع

### A — إغلاق المخاطر العالية

PR01–06 مع D1 مبكرًا إذا اكتمل. يراجع كل PR مستقلاً؛ لا يشترط انتظار اكتمال إعادة التنظيم لنشر إصلاح أمان المال بعد بواباته. تنشر تباعًا حسب التوافق، مع snapshot للنسخة والإعدادات وأعداد الصفوف قبل كل دفعة.

### B — البيانات وعقود الداشبورد

PR07 توسعة schema ثم نسخة writer/reader المتوافقة. نتحقق من صرف جميع النسخ والعمال القديمة قبل canonicalization وPR08. PR10 backend contract أولًا ثم adapter frontend؛ PR11 endpoint تجميعي إضافي ثم المستهلك. لا تغيير response قديم على نحو كاسر أثناء rolling deployment.

### C — العقود والتنظيم والأداء

PR12–15 بعد استقرار A/B؛ PR16 يمكن إعداد dry-run مبكرًا وتشغيل الإصلاح التاريخي بعد اعتماد manifest وتثبيت قواعده. تبقى ميزة التصدير الخلفي اختيارية حسب القياس، لا شرطًا مصطنعًا لإغلاق P1.

### قائمة تنفيذ كل دفعة

- [ ] تسجيل SHA/image وmigrations وconfiguration revision المستهدفة وقابلية binary السابق لقراءة schema الجديدة.
- [ ] التأكد من backup/restore المجرب، وصحة بيئة التنفيذ، وعدم وجود مزود مالي مجهول النتيجة يتأثر بخطوة قطع الاتصالات.
- [ ] تطبيق additive migrations بتحديد lock_timeout وstatement_timeout المناسبين بعد rehearsal؛ فشل الحصول على القفل يؤدي إلى إيقاف الدفعة دون قتل جلسات العملاء أو تعطيل القيد.
- [ ] نشر backend المتوافق، ثم consumer/worker عند الحاجة، ثم dashboard؛ صرف الاتصالات والمهام القديمة برشاقة. لا canary لكاتب جديد مع قديم غير متوافق.
- [ ] تحقق مصادق عليه من الرحلات الحرجة. المدفوعات الخارجية في sandbox؛ لا تُنشأ charge حقيقية لمجرد smoke. عمليات الإنتاج الاختبارية تحتاج تفويضًا محددًا.
- [ ] مراقبة مكثفة لأول ساعتين عمل، ثم يوم عمل كامل، ثم مراجعة بعد سبعة أيام. لا انتظار صامت مطلوب من المنفذ؛ يوثق فريق التشغيل النتائج. أي أتمتة مراقبة تحتاج طلبًا منفصلًا.
- [ ] توثيق أثر النسخة الجديدة والحالات المفتوحة وقرار الاستمرار أو التراجع.

**إشارات إيقاف فورية:** تحصيل زائد جديد واحد؛ تغير مبلغ/هوية سجل تاريخي دون manifest؛ استرداد أو رسالة خارجية غير مقصودة؛ حجز نشط فقد الشخص؛ فقد حدث مطلوب بعد commit؛ endpoint يوسع الوصول. لا نعيد تشغيل التحصيل تلقائيًا لعلاج أي منها.

**أهداف مراقبة أولية للمراجعة:** queue lag للأحداث المالية أقل من 60 ثانية في الحمل الاعتيادي، دون FAILED متزايد؛ p95 لا يتراجع أكثر من 10% عن baseline تحت الحمل نفسه؛ لا زيادة في 5xx أو deadlocks. الأهداف مقترحة وليست قياسات إنتاج قائمة، وتُضبط في B0 قبل الإطلاق.

**Rollback:** أعد binary متوافقًا بالمسار المعتمد، واترك الأعمدة/الفهارس الإضافية إن كانت آمنة. لا drop ولا reverse migration يفقد بيانات. لا ترجع قبل النسخة التي تفهم supersededAt بعد تسوية intake، ولا قبل نسخة outbox المتوافقة بينما الأحداث الجديدة قيد التسليم. إذا كانت النسخة القديمة تعيد عيب تحصيل مثبتًا، استخدم forward-fix أو تعطيلًا مؤقتًا محدودًا لبدء العملية المتضررة مع مسار تشغيل معتمد؛ لا تعتبر إعادة العيب rollback ناجحًا. استعادة backup فوق الإنتاج إجراء تعافٍ استثنائي بقرار منفصل ومصالحة لكل كتابة لاحقة.

## 8. خطة زمنية وتكلفة جهد تقديرية

| المرحلة | الجهد التقديري | شرط الخروج |
|---|---|---|
| B0 وO1 | 2–3 أيام هندسية | بيئة آمنة وبوابة DB حقيقية |
| F1–F3 وT1–T2 | 6–9 أيام هندسية | إغلاق الخمس P1 باختبارات فشل وتزامن |
| T3–T4 وD1–D4 | 5–8 أيام هندسية | سلامة intake وعقود وعرض صحيح |
| O2–O4 وR1 والتكامل | 5–8 أيام هندسية | حدود قابلة للقياس وتقارير أخف ومصالحة مراجعة |

الإجمالي **18–28 يومًا هندسيًا تقديريًا**، إضافة إلى زمن قرارات المالك والوصول ونافذة التشغيل ومراجعة الحالات التاريخية. مع تنفيذ متوازٍ مضبوط يمكن ضغط الزمن التقويمي؛ لا نضغط فترة مراقبة البيانات أو نعد بتاريخ تسليم قبل B0. تصدير خلفي أو عدد كبير من السجلات التاريخية المتعارضة قد يضيف جهدًا يُقاس ويُعرض قبل توسيع النطاق.

## 9. تعريف التسليم النهائي

- [ ] إغلاق كل رقم P1/P2 بدليل أو قرار تأجيل محدد ومدعوم بقياس؛ لا استبدال «لم يُختبر» بـ«سليم».
- [ ] جميع رحلات القبول الحرجة نجحت على SHA المرشح، وreal-DB الأساسية بلا skip، وsandbox للمسار المالي المتأثر مكتمل.
- [ ] لا تغييرات كبيرة في الواجهة؛ مقارنة عربية/RTL تثبت أن الفرق ضمن الجدول في التصميم.
- [ ] البيانات السابقة لها manifest مراجَع ونتيجة تصحيح أو قائمة حالات تحتاج صاحب القرار، دون إخفاء أو حذف.
- [ ] runbook للنشر والتراجع والمصالحة، ونسخة منشورة مثبتة، ونتائج مراقبة بعد النشر.
- [ ] إذا لم يتوفر تفويض نشر أو وصول إنتاج، يكون التسليم «جاهز محليًا/للمراجعة» بدليله، ولا يعلن اكتمال التحسين في الإنتاج.
