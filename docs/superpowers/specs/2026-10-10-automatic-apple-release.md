# أتمتة Apple لتطبيق سواء الواحد

الحالة: اختيارات المالك معتمدة في المحادثة؛ خطة التنفيذ معتمدة ويجري تنفيذها. لم تُفعّل الأتمتة بعد.

## القرارات المعتمدة

- التطبيق الحالي فقط: `sa.sawa.app`، الفريق `569M49FYA6`، App Store Connect `6815632181`.
- بناء `develop` يتصل بـ `https://staging.sawaa.sa/api/v1`.
- بناء `main` يتصل بـ `https://api.sawaa.sa/api/v1`.
- تثبيت بناء الاستيج أو الإنتاج يستبدل التطبيق الآخر. الرابط ثابت داخل البناء؛ لا توجد شاشة تبديل بيئات.
- البناء على GitHub macOS والتوقيع الحالي في GitHub Secrets؛ لا اشتراك EAS جديد ولا اعتماد على بقاء جهاز المالك يعمل.
- يبقى بناء صور الخادم داخل OpenShip. لا انتقال إلى GHCR.
- نشر الخادم للإنتاج ودمج `develop` إلى `main` يتطلبان قبول الاستيج وأمر الإنتاج الصريح وفق السياسة.
- الأتمتة ترفع إلى TestFlight فقط. اختيار بناء المتجر وإرساله للمراجعة وإطلاقه مرحلتان منفصلتان.

## التسلسل

1. تحديث الفرع عبر PR وفحوصه المطلوبة.
2. OpenShip ينشر الفرع في مشروعه الحالي.
3. GitHub يتحقق من المشروع والفرع والـ SHA الفعلي والنشر النشط وحالة الخدمات، ثم يفحص جاهزية API والموقع واللوحة إذا كان لها رابط عام. لوحة الاستيج داخلية ويُتحقق من حاويتها والنشر، مع فحص HTTP داخلي في قبول النشر. إذا سجل OpenShip `no_changes` لنفس SHA الجديد، لا يكفي وحده: يجب إثبات تطابق جميع ملفات الخادم مع النشر النشط الجاهز، وتسجيل SHA التطبيق وSHA النشر كلٌ على حدة.
4. إذا نجح النشر، GitHub يبني iOS بواسطة Expo prebuild وXcode، بنفس التوقيع والمعرف الحاليين.
5. يراجع السكربت IPA: الرابط الصحيح، معرف التطبيق، الإصدار والبناء، توقيع التوزيع، القدرات والملفات اللازمة.
6. يرفع البناء، ينتظر Apple حتى `VALID`، ويضيفه إلى مجموعة `Sawaa Internal`، ويتحقق من توفره.
7. يسجل SHA والبيئة ورقم البناء ومعرف Apple ونتائج الفحص في أثر إصدار خالٍ من الأسرار.

تغييرات التوثيق وحدها لا تبني تطبيقًا. تشمل مدخلات البناء ملفات الجوال وshared وملفات الاعتمادات والأتمتة. أي فشل أو مهلة ينهي التشغيل قبل المرحلة التالية. إعادة تشغيل Actions لا تعيد رفع بناء سبق قبوله؛ نتيجة رفع غير مؤكدة تتطلب الاستعلام قبل إعادة المحاولة.

## إعدادات وأسرار

شهادة التوزيع P12 وكلمة مرورها، ملف التهيئة الحالي، مفتاح App Store Connect ومعرفه ومعرف المصدر، وملف Firebase الحالي. تُحفظ داخل Secrets وتُستعاد في مجلد مؤقت ومفتاح توقيع مؤقت يُحذف بعد التشغيل. لا يطبع السكربت الأسرار ولا يرفع مواد التوقيع كآثار.

للتحقق من OpenShip، يستخدم كل مشروع مفتاح قراءة محدودًا بالمشروع؛ لا تُنقل مفاتيح SSH الإدارية إلى GitHub ولا يُسمح لهذا المفتاح بالنشر أو تعديل البيئة. إنشاء المفتاح ونقله يحتاج تنفيذًا موثقًا بعد تحديد صلاحياته فعليًا. لا يتم تعطيل النشر التلقائي الحالي.

## التوافق والأمان

يحافظ البناء على Apple Pay وAPNS وFirebase والخطوط ومكوّن الدفع الأصلي. لا تغييرات في المصادقة أو الدفع أو قواعد البيانات ضمن هذه الأتمتة. تبديل البناء على الجهاز قد يبقي تخزين التطبيق؛ جلسة إحدى البيئتين لا تُعد جلسة صالحة للأخرى. تُراجع طريقة فصل التخزين الموجودة قبل أي تغيير، وتُعرض أي حاجة لتغيير المصادقة على المالك قبل التنفيذ.

لا تتيح الأتمتة بناءً للإنتاج من `develop` أو بناءً للاستيج من `main`. لا تجعل البناء 35 الحالي إنتاجيًا: ملفه الحالي مرتبط بالاستيج. النسخة النهائية للإنتاج تحتاج بناءً جديدًا بعد ترقية المصدر المعتمد.

## القبول

- فحوص آلية ترفض رابط البيئة المعاكس والفرع غير المعروف وSHA القديم والنشر الجزئي والخدمات غير الجاهزة.
- بناء موقع محليًا بالطريقة الجديدة، والتحقق من IPA دون رفعه لمجرد الاختبار.
- تشغيل GitHub على `develop` مع إثبات نشر OpenShip المطابق، ثم `VALID` وتوفر البناء في المجموعة.
- إنتاج `main` يُختبر بعد تصريح ترقية الإنتاج؛ لا تُدعى جاهزيته التشغيلية قبل ذلك.
- اختبار المالك على جهاز حقيقي والدفع ومقدمو الرسائل تبقى قبولًا منفصلًا.

## إصلاح OpenShip

له مسار تشخيص مستقل. نجحت أبنية BuildKit صغيرة متتالية عبر التصحيح الموجود في النسخة 0.8.0، لذلك لا يكفي ذلك لنسبة تعليق البناء الحقيقي إلى Bun وحده. يجب إعادة إنتاج التعليق في بناء سواء الفعلي، وتحديد نقطة الانتظار، واختبار الإصلاح قبل تغيير حاوية التحكم المشتركة. تحديث المنصة كلها أو ترحيل قاعدة بياناتها يحتاج مراجعة نطاقه، ولا يُنفذ باعتباره إصلاحًا تلقائيًا بسيطًا.
